## 2. 业务流速览（一页图 + 面试口述）

**知识入库（一次）**：产品说明书 / 政策规则 Markdown → `scripts/build_finance_kb.py` 按 `##` 分节 → chunk(`chunks_processed.jsonl`) → bge 向量入 **Milvus** + 重建 BM25 → **213 chunks**。图谱：`kg_triples.jsonl` 156 三元组 → Neo4j。

**问答（每次）**：

```
提问 → 会话/改写 → ★网关语义缓存(命中即返) → 规则路由
   ├─ greeting/simple_fact → 快速通道(检索+廉价模型)
   └─ complex → LangGraph 编排 / AnalystAgent
         → RouterAgent(12 类理财意图) ∥ 两路召回(Milvus+BM25)
         → 槽位抽取(product/金额/期限/R等级) → Orchestrator 派发
              ├─ 8 类咨询意图 → finance_node(只读工具循环+图谱多跳注入)
              ├─ BUY_PROCESS+product → subscribe_node(申购确定性门控:
              │      归属→适当性→起购金额→验证码二次确认→写持仓+留痕)
              ├─ fraud/complaint → handoff_node(确定性转人工)
              └─ chitchat → 闲聊
         → Reviewer 反幻觉 → 出站合规(PII掩码/风险提示) → 答案+溯源(🕸️图谱路径)
```

### 面试 2 分钟口述脚本

「这个项目是一个**金融/银行理财产品智能客服**，底层是一套领域无关的智能客服底座（LangGraph 多 Agent 编排 + 混合检索 + 分层记忆 + 语义缓存 + 人工坐席闭环），当前挂载金融理财域。问答先查网关语义缓存，命中直接返回、不碰大模型；没命中走规则路由，寒暄和简单知识问题走快速通道省钱，复杂问题才进 LangGraph 状态机。

进了完整链路就是三个 Agent 协作加一道确定性门控：RouterAgent 用"规则快分类 + LLM few-shot"把问题分成 12 类理财意图（产品咨询/对比/适当性/收益口径/存款保险/购买流程/持有赎回/费用/风险举报/投诉等），未知直接礼貌拒答；领域 Agent 用只读工具循环查产品、查适当性、查本人持仓；最后 Reviewer 做反幻觉验证，答案要能溯源到知识库或图谱文档。

理财场景最关键的是**资金动账**：想买产品时系统走**确定性申购门控**——先做适当性匹配（客户测评等级不能低于产品风险等级，不匹配直接提示并转人工/双录），再校验起购金额、要短信验证码二次确认，全过才写持仓并审计留痕。**资金动账我根本不注册成大模型能自由调用的工具**，所以模型想"自觉放行"在结构上都不可能。

对"银行理财是存款吗、存款保险赔吗"这类需要跨知识的关系问题，我在两路文本检索之外接了**知识图谱多跳**：156 条金融三元组（存款保险覆盖/不保、代销边界、保险犹豫期、适当性、征信链），命中就沿图找路径、把带文档溯源的推理句喂给模型。出站还会过合规层：手机/身份证/卡号强制掩码，"稳赚、零风险、承诺保本"这类话被拦，非存款产品涉收益自动补风险提示；"我的持仓、验证码"这类用户私有问答不进共享缓存防串户。结果：266 项单测通过，金融 Golden QA 离线评测证据覆盖 100%、多跳路径与图谱一致率 100%。」

## 4. 端到端请求链路

### 4.1 同步 `/chat/sync` 与流式 `/chat/stream`

```
请求(query + session_id + user_id)
 ① 会话状态 + 查询改写(多轮指代)
 ② ★ 网关语义缓存(get_cached) — 命中直接返回
     守卫: 用户私有/动账类(privacy.py) 不读不写; 语义高相似但关键要素不同→拒
 ③ 规则路由(ms): greeting / simple_fact / complex
 ④ complex → ★ LangGraph(stream) 或 AnalystAgent(sync):
     classify → memory → route_retrieve(意图∥检索) → slot_check → orchestrator
        ├─ 8 类咨询 → finance_node: AgenticAgent(FINANCE_KB prompt)+只读工具+图谱注入
        ├─ BUY_PROCESS(有 product) → subscribe_node: 适当性→金额→验证码→写持仓+留痕
        ├─ FRAUD/COMPLAINT → handoff_node(静态话术 + handoff=True)
        └─ CHITCHAT/UNKNOWN → 闲聊/礼貌拒答
     → reviewer(确定性门控/高置信跳过 LLM 审核) → formatter
 ⑤ 出站合规(compliance.finalize: PII 掩码/禁语/风险提示)
 ⑥ gateway_cache.set_cache(通用产品问答可写; 用户私有/动账不写) + 记忆回写
```

> **白话解读**：一个理财提问进来的顺序是"先捡便宜（会话/缓存/规则），贵的 LLM+门控留给复杂"。缓存前有隐私守卫——"我的持仓/验证码 123456"这类绝不进共享缓存，防止另一个用户命中别人的答案。买产品的对话会进入确定性申购门控，而不是让模型随口承诺。

### 4.2 确定性申购门控（subscribe_node）

```
BUY_PROCESS + 目标产品(product 槽)
  → 归属: 绑当前 user_id
  → 适当性: 产品 risk vs 测评等级(investor_level)
        不足 → 风险提示 + 转人工/双录(handoff), 不执行
  → 起购金额校验
  → 短信验证码二次确认(缺/错 → 追问; 连续多轮由 checkpointer 承接)
  → 写持仓(mock_finance) + Redis security:events 审计
  → 返回确认 + 风险提示语
```

> **要点（面试）**：资金动账 **不注册为模型可自由调用的工具**——模型只有只读能力，放行是系统代码做的确定性判定，不是模型自律。这是"能确定性判断就不赌模型自觉"的落地。

## 5. 意图路由与槽位

两级路由：`query_router.classify`（规则：greeting/simple_fact/complex，词表理财化）→ `RouterAgent.route`（LLM few-shot JSON 输出 12 类意图 + 实体；异常走关键词/正则规则兜底，顺序按资金安全敏感度：诈骗→投诉→存款保险→适当性→费率→持有→购买→对比→收益→产品→闲聊）。

`slot_filler.extract_slots`：产品名（读 `catalog.jsonl` 全名，口语靠 alias）、产品大类、金额（归一万元）、期限、R 等级。`missing_required` 阶段二在申购流程补 product/amount 校验（缺则追问）。

## 6. 检索与知识图谱

### 6.1 两路文本 + 图谱多跳

```
query
 ├─ Path A 向量(Milvus) bge encode → top_k*3 → MMR 重排(λ 可配)
 ├─ Path B BM25 → top_k*3
 └─ RRF 融合 → local top_k
 ★ 图谱(GraphRetriever): 实体解析(产品/概念别名)→ 双实体有向路径(≤3跳)+邻居
     仅"关系类/多实体"问题注入 1~3 条 `知识图谱-<doc>` 证据(实体对齐防噪音)
返回 {local(含图谱证据), graph}
```

### 6.2 图谱构建与溯源

- 三元组 90 条：产品 is_type_of/risk_level/受存款保险保障；存款保险 covers 存款、excludes 理财/基金/保险；代销边界；保险犹豫期；适当性红线；逾期→征信→房贷。
- 每个三元组 `doc` 挂回 KB 文档 → 推理句带"（依据 xxx.md）"。
- 后端：Cypher over Neo4j（`src/knowledge_graph/core.py`）。Neo4j 不可用时图谱检索**直接报错** —— 不再降级内存邻接（两个后端的图可能不一致，静默换源等于悄悄改变答案依据）；单测/离线调试可显式传 `backend="memory"`。
- 概念枢纽（理财/存款/基金/保险）不做单实体邻居展开，防泛化噪音。

> **白话解读**："银行理财是存款吗、存款保险赔吗"靠向量像不像答不准，要靠"理财 不是 存款、存款保险 只保 存款"这种**关系路径**。图谱把散在各文档的政策关系串成可遍历的图，复杂问题沿图给出带溯源的推理链；生产用 Neo4j；不可用时图谱相关查询明确报错，而不是换一个数据源。

## 7. Reviewer 反幻觉 + 合规出站

```
Agent 答案 + contexts
  → QuickCheck(正则): 数字/单位(元/万/%/年化等)必须在检索上下文; 来源合法
        ~60% 在此放行(跳过 LLM)
  → 确定性门控/高置信 跳过 LLM 审核(subscribe/handoff 节点)
  → 其余 → LLM 审查, reject ≤2 次重写
出站: compliance.finalize(answer)
  → PII 掩码(手机/身份证/银行卡 只留首尾)
  → 金融禁语(稳赚/零风险/承诺保本…)打星
  → 非存款产品涉收益且无提示 → 追加"理财/基金/保险非存款，产品有风险，业绩比较基准等不构成收益承诺"
```

> **白话解读**：Reviewer 是"出厂质检"——核对答案数字/来源是否有材料支撑。合规层是金融特有的第二道：用户的卡号手机号绝不允许原样出站；理财话术不能滑向"稳赚/保本承诺"；存款类（大额存单）不误加"理财非存款"提示。

## 10. 容错与降级

**原则：降级不许静默。** 判断标准只有一条 —— 这个降级会不会让用户拿到「错误的或缺失的答案」而系统自认为正常？
会 → 删掉；不会（只是慢/贵）→ 保留，但必须在 `/health` 与前端状态里看得见。

**已删除的降级**（都会改变"答什么"）
- 向量后端不再有 FAISS 分支：Milvus 是唯一后端，不可用时检索直接报错，不返回空结果冒充"没找到"。
- BM25 索引缺失或返回 0 条直接报错 —— 原来的静默退化正是「假混合检索」缺陷的成因（表面上混合检索，实际只有向量一路）。
- 图谱不再降级内存邻接：两个后端的图可能不一致，静默换源等于悄悄改变答案依据。
- 上传不再降级同步线程：Celery Worker 不在时直接拒绝，免得两条路径产出不同分块。

**保留的降级**（只影响速度，不影响答案）
- Redis 缓存/语义缓存不可用降级 no-op；SQLite 语义缓存回落；审计计数失败不阻塞响应。
- 以上都会在 `/health` 与前端服务状态里如实显示，不静默。
- 重排接口失败：记 ERROR 并沿用融合原序，同时在返回体里带 `rerank_failed` 字段，让"重排没生效"可被上层与评测看见。

**其他**
- AgenticAgent 工具循环失败 → 预取检索 + 普通 chat 回退（复用同一检索逻辑）。

## 16. 意图分层架构改造（2026-10 增强）

### 16.1 改造背景

原系统采用 **12 类平面意图结构**（`QueryIntent` 枚举），存在三个短板：

1. **意图平面化，无法扩展**：新增产品域需要修改枚举和所有映射，扩展性差
2. **槽位校验预留接口但未激活**：`missing_required()` 返回空列表，产品缺失时不追问
3. **DST 焦点字段不匹配**：`DialogState` 的 `focal_company/focal_metric` 是金融分析遗留，客服槽位是空壳

### 16.2 二维意图分层设计

将意图从 12 类平面结构改为 **L0 产品域 × L1 问询类型** 的二维分层：

| 层级 | 含义 | 取值 | 决定什么 |
|------|------|------|---------|
| **L0** | 产品域 | deposit / wealth / fund / insurance / common / out_of_scope | 用哪个 system prompt、检索哪些文档、必需哪些槽位 |
| **L1** | 问询类型 | product_info / income / fee / risk / buy_process / redeem / compare / compliance | 回答侧重、合规提示 |
| **L2** | 具体操作 | LLM 动态提取（可选） | 精细化处理 |

配置文件：`config/intents.yaml`（L0/L1 定义 + Jev 配置）、`config/agents.yaml`（各域 prompt/槽位/合规）

### 16.3 Jev L0 快速分类

`src/agents/jev_classifier.py`：用 TypeSafe Jev（System One 模型）Choice 原语做 L0 6 选 1 分类。

- 置信度路由：`>0.85` 跳过 LLM，`0.60~0.85` 传 LLM 参考，`<0.60` LLM 全分类
- 双后端：TypeSafe 官方 API 或 OpenRouter（`typesafe/jev-latest`）
- 静默降级：API 不可用时返回 `(None, 0.0)`，不影响主流程
- 验证脚本：`scripts/eval_jev_l0.py`（40 条 Golden QA）

### 16.4 RouterAgent 分层路由

`src/agents/router_agent.py` 新增 `route_layered()`：规则粗筛 → Jev L0 → LLM L1/L2 + 槽位 → 话题切换检测。保留原有 `route()` 向后兼容。

### 16.5 DST 扩展

`src/core/dialog_state.py` 新增：`current_l0/l1/l2`、`topic_stack`（话题栈，支持"回到刚才"）、`negative_turns`、`turn_count`、`emotion`。方法：`push_topic()` / `pop_topic()` / `reset_topic()`。

### 16.6 槽位校验激活

`src/core/slot_filler.py` `missing_required()`：传 `l0` 时从 `agents.yaml` 读取 required_slots，不传时按意图映射默认（向后兼容）。`cs_graph.py` `slot_check_node` 调用 `_intent_to_l0()` 推断产品域，缺失时设置 `awaiting_slot` 并追问。

### 16.7 情绪处理

`src/core/emotion.py`：关键词规则（不引入模型），四类情绪 normal/anxiety/complaint/confusion。`detect_emotion()` + `build_emotion_instruction()` + `should_suggest_handoff()`。

### 16.8 知识库运营工具

`scripts/kb_ops.py`：`--queue` 低置信度审核队列、`--hotspot` 热点问题分析、`--gap` 知识库覆盖缺口。输出到 `data/kb_ops/`。

### 16.9 新增文件清单

## 18. 多问题拆分与完整数据流转（2026-10）

### 18.1 多问题拆分（Decompose）

`src/core/query_decomposer.py`：解决用户一次问多个独立问题时检索覆盖不全的问题。

- **LLM 拆分**：将用户输入拆成可独立检索的子问题列表，JSON 数组输出
- **快速路径**：没有问号/分号/连接词时直接返回 `[原问题]`，不调 LLM，零延迟
- **降级策略**：LLM 调用失败/格式异常时降级返回 `[原问题]`，不阻断主流程
- **子问题上限**：5 个，防过度拆分
- **接入位置**：`cs_graph.py` `route_retrieve_node` 内部，路由仍用原始 query，检索用拆分后的子问题并行检索后合并去重
- **图结构不变**：不新增 LangGraph 节点，下游节点零改动

**检索覆盖度提升**：3 个多问题用例平均新增 +4.7 个 chunk / +2.7 个来源文档。

```
  │  └─ 会话状态加载 (Redis)
  │

③ 规则路由 (src/llm/query_router.py classify)
  │  ├─ greeting → 快速通道 (greeting_node, 廉价LLM)
  │  ├─ simple_fact → 快速通道 (simple_fact_node, 检索+廉价LLM)
  │  └─ complex → 完整 LangGraph 状态机
  │
  ▼ (complex 路径)
④ LangGraph 状态机 (src/graph/cs_graph.py)
  │
  ├─ classify_node: 规则快分类 (greeting/simple_fact/complex)
  ├─ memory_node: 三层记忆注入 (会话窗口+用户画像+向量语义记忆)
  ├─ route_retrieve_node: ★ 路由 ∥ 检索 并行
  │     ├─ 路由: RouterAgent.route_layered() → L0产品域 × L1问询类型 + 实体 + 置信度
  │     ├─ Query Rewriting: 指代补全 (规则层, 零延迟)
  │     ├─ Decompose: 多问题拆分 (LLM, 单问题跳过)
  │     ├─ 检索: HybridRetriever (Milvus向量 + BM25) → RRF融合 → MMR重排
  │     │     └─ 多子问题并行检索 → 按chunk_id去重合并 → 取top-K
  │     ├─ 图谱多跳: GraphRetriever (关系类问题触发, Neo4j Cypher)
  │     └─ 一致性校验: 路由置信度<0.7 且检索top3集中于另一主题 → 修正意图
  │
  ├─ slot_check_node: 槽位抽取 + 缺失追问 (missing_required, 按L0读agents.yaml)
  │     └─ 缺失 → 追问 (awaiting_slot), 结束本轮
  │
  ├─ orchestrator_node: 按意图派发
  │     ├─ 8类咨询意图 → finance_node (AgenticAgent, 只读工具循环+图谱注入)
  │     ├─ BUY_PROCESS+product+amount → subscribe_node (确定性申购门控)
  │     ├─ FRAUD/COMPLAINT → handoff_node (确定性转人工)
  │     └─ CHITCHAT/UNKNOWN → 闲聊/礼貌拒答
  │
  ├─ reviewer_node: 反幻觉审核
  │     ├─ QuickCheck (正则): 数字/来源有上下文支撑 → ~60% 跳过LLM
  │     ├─ 确定性节点 (subscribe/handoff) 跳过LLM审核
  │     └─ 其余 → LLM审查, reject → regenerate_node 重写 (上限1次)
  │
  └─ formatter_node: 格式化输出
  │
  ▼
⑤ 出站合规 (src/core/compliance.py finalize)
  │  ├─ PII 掩码 (手机/身份证/银行卡 前3后4)
  │  ├─ 金融禁语拦截 (稳赚/零风险/承诺保本)
  │  └─ 风险提示自动附加 (非存款产品涉收益)
  │
  ▼
⑥ 回写
  │  ├─ 语义缓存写入 (通用产品问答, 私有/动账不写)
  │  ├─ 记忆回写 (memory_store.save_turn)
  │  ├─ 审计留痕 (Redis security:events, 工具调用/动账)
  │  └─ Badcase 记录 (turn_traces 表: 未知意图/检索为空/审核reject/低置信度/用户点踩)
  │
  ▼
返回用户 (answer + sources + handoff + review)
```

### 18.3 评测体系运作的数据流转

项目评测分四层，每层有独立脚本和数据产物：

```
┌─────────────────────────────────────────────────────────────┐
│ 第一层：检索层评测 (无需LLM, 秒级)                           │
│ 脚本: scripts/eval_retrieval.py                              │
│ 输入: scripts/eval_qa.jsonl (56条, 自动生成)                │
│ 流程: 每条问题 → HybridRetriever → 比对 golden_chunk_ids     │
│ 输出: Recall@K, MRR, 逐条命中排名                            │
│ 选项: --with-rewrite (对比改写前后), --by-evidence (文件名级)│
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│ 第二层：离线静态评测 (无需LLM, 分钟级)                        │
│ 脚本: scripts/eval_finance.py (默认模式)                     │
│ 输入: data/eval/finance_qa_golden.jsonl (105条 Golden QA)  │
│ 流程: 每条 → 检索器+图谱检索器 → 四项指标:                    │
│   ① 证据覆盖率 (evidence文档是否在检索结果来源中)             │
│   ② chunk信息命中率 (检索到的段落是否包含答案关键词)          │
│   ③ 图谱路径结构一致率 (Golden期望路径是否真实存在于图谱)     │
│   ④ 图谱触发率 (关系类问题是否触发图谱多跳查询)               │
│ 输出: data/eval/report_finance.json                           │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│ 第三层：在线端到端评测 (需LLM, 耗时较长)                      │
│ 脚本: scripts/eval_finance.py --with-answers                 │
│ 输入: 105条 Golden QA                                         │
│ 流程: 每条 → 完整对话链路 (路由+检索+生成+审核+合规)          │
│       → 比对最终意图 vs Golden标注意图                         │
│       → 检查答案合规 (PII/禁语/风险提示)                      │
│ 输出: 意图准确率, 合规通过率, 逐条trace                       │
│ 触发: sync_kb.py --with-answers (知识库同步后自动回归)       │
└─────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│ 第四层：统一评测报告 (整合前三层)                              │
│ 脚本: scripts/eval_unified.py                                 │
│ 输入: report_finance.json + 在线结果 + 延迟基准               │
│ 输出: data/eval/report_unified.json (功能+性能一页展示)      │
│ 看板: frontend EvalPage (可视化进度条+基线对比)               │
└─────────────────────────────────────────────────────────────┘
```

**Golden 绑定知识库版本**：`scripts/golden_bind_version.py` 给每条 Golden 加 `kb_version` 和 `evidence_hashes`（SHA256），知识库更新后自动检测哪些 Golden 的 evidence 变化或缺失，标记需复核，防止标准答案过期。

### 18.4 失败案例沉淀与迭代闭环

项目建立了完整的 badcase 从发现到沉淀到迭代的闭环：

**1. 自动采集（5 类 SQL 谓词派生）**

用户每轮对话的 trace 写入 `turn_traces` 表，badcase 候选由以下条件自动派生（无需人工标记）：

| 类型 | 触发条件 | 说明 |
|------|---------|------|
| 未知意图 | 路由结果为 UNKNOWN | 意图分类覆盖不足 |
| 检索为空 | 检索结果 top-K 为空 | 知识库覆盖缺口或分块问题 |
| 审核 reject | Reviewer 判定答案无支撑 | 答案幻觉或检索不准 |
| 低置信度 | 路由置信度 < 0.6 | 意图边界模糊 |
| 用户点踩 | 前端反馈 thumbs_down | 用户主观不满意 |

**2. 自动聚类分诊**

`scripts/badcase_cluster.py`：
- 从 turn_traces 加载 badcase 候选
- 用 BGE embedding 对问题向量化
- 按余弦相似度贪心聚类（阈值 0.75 可配）
- 自动标注类型（检索失败/意图错误/审核不通过/低置信度/其他）
- 按簇大小排序，输出到 `data/kb_ops/`

**3. 人工分诊与提升**

前端 `BadcasePage`（质量复盘页）：
- 展示聚类后的 badcase 簇
- 人工分诊：确认问题类型、标注根因
- 一键提升为 Golden QA：`evidence` 故意留空（因为 badcase 成因常常是检索错了，自动填入当轮召回等于把 bug 固化），必须人工补齐
- 提升后 Golden 自动绑定当前知识库版本指纹

**4. 回归评测与迭代**

- `sync_kb.py --with-answers`：知识库同步入口挂回归评测，指标下降即返回非零退出码
- 评测结果按知识库指纹归档到 `data/eval/history.jsonl`
- 看板绘制基线对比趋势，指标下降自动告警
- 形成"发现 badcase → 聚类分诊 → 提升 Golden → 回归评测 → 指标验证"的闭环

**5. 知识库运营工具**

`scripts/kb_ops.py`：
- `--queue`：低置信度审核队列（需要人工补全或修正的问题）
- `--hotspot`：热点问题分析（高频未命中问题，指导知识库扩充方向）
- `--gap`：知识库覆盖缺口分析（检索为空的问题聚类，识别哪些主题缺文档）
