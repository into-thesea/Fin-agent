## 二、离线检索评测（无需 LLM，全量 105 条）

离线评测直接调用检索器与图谱检索器，不经过大模型，运行快、可重复，是改动检索、分块、图谱代码后最常跑的一层。

### 2.1 四项离线指标（当前值）

| 指标 | 当前值 | 计算方式 |
| --- | --- | --- |
| 证据覆盖率 | 99.0% | Golden 标注的 evidence 文档是否出现在检索结果的 source 中，仅统计有 evidence 标注的用例 |
| chunk 信息命中率 | 98.0% | 检索到的 evidence 文档段落中是否真正包含问题答案；比文档级覆盖更严格——文档命中但段落不相关不算 |
| 图谱路径结构一致率 | 83.3% | Golden 标注的 expected_path 三元组是否真实存在于图谱中（验证图谱与 Golden 自洽，属数据一致性，不是测检索） |
| 图谱触发率 | 45.7% | 对全部 105 条跑图谱检索，统计关系类问题是否触发并返回路径证据 |

### 2.2 chunk 信息命中率的口径与真实归因（重点）

该指标在项目过程中经历了 `67.3% → 68.4% → 98.0%` 的变化，需要区分“检索本身的变化”和“评测方法的变化”，否则会把评测口径修正误当成检索能力的飞跃：

1. **67.3%（初始，字符 n-gram 精确匹配 + 旧分块）**：评测要求问题中的连续字符片段逐字出现在段落里。
2. **67.3% → 68.4%（检索参数调优的真实提升，+1.1pp）**：调小分块、增大重叠、top_k 5→8、MMR λ 0.5→0.7。
3. **68.4% → 98.0%（主要是评测方法修正）**：字符 n-gram 精确匹配对“口语提问 vs 书面知识”存在系统性假阴性，包括虚词插入（“首次线上” vs “首次在线上”）、词序变化（“退保超了犹豫期” vs “超过犹豫期退保”）、标点差异（“R3 平衡型” vs “R3（平衡型”）、同义改写（“两家银行各存” vs “同一存款人在同一家”）。改用 **jieba 中文分词做词级匹配**，并用 **embedding 语义相似度（阈值 0.55）独立交叉验证**，两种方法结果一致，均为 98.0%，从而还原了检索的真实水平。
4. **父子分块的边际贡献经 A/B 实测为 0pp**：在同一评测口径下，对比“旧形态直接检索父块”与“新形态子块检索后展开父块”，chunk 命中率没有差异。父子分块的价值在于检索单元更聚焦、返回上下文更完整（见 2.3），但并不是把命中率从 68% 拉到 98% 的原因；这一点如实记录，不夸大。

### 2.3 知识库最终形态

- 分块结构：**213 个父块（章节级完整内容）+ 252 个子块（句子级检索单元）= 465 块**。
- 父块：以文档的章节（`##` 标题）为单位，保留该章节的完整内容，作为最终返回给模型的上下文。
- 子块：父块按中文句子边界（句号/问号/感叹号/分号）二次切分为约 150 字符、30 字符重叠的检索单元，携带父块章节标题前缀与 `parent_id`。
- 向量检索（bge-base-zh-v1.5，768 维 + Milvus）与稀疏检索（BM25 中文 bigram）**都只索引 252 个子块**；子块命中后经 `parent_id` 展开为父块完整章节，同一父块自动去重。
- 融合机制：RRF 倒数排名融合（k=60）+ MMR 多样性重排（λ=0.7）；语义精排为可配置开关，当前关闭。
- 知识图谱：Neo4j 存储 **180 条三元组**，多跳检索触发率 45.7%。
- 产品目录：**24 款产品**，覆盖自营存款/理财/账户黄金与代销基金、保险、国债、信托等大类。

## 五、延迟专项测试（40 条固定样本实测）

### 5.1 测试方法

- 固定测试集：从 Golden QA 按意图分层选取 40 条，可复现。
- 预热排除冷启动：正式测量前先跑 3 条，使嵌入模型、Milvus、LLM 连接全部就绪，预热数据不计入。
- 端到端计时：调用完整对话入口，测量从问题进入到回答返回的真实耗时。
- 阶段基准：独立测量检索、路由各自耗时，用于定位瓶颈（不与总耗时简单相加，因复杂路径下路由与检索并行）。

### 5.2 端到端延迟分布（秒）

| 路径 | n | 平均 | P50 | P90 | P95 | min | max |
| --- | -- | ---- | ---- | ---- | ---- | ---- | ---- |
| 整体 | 40 | 6.66 | 6.17 | 8.75 | 10.09 | 3.26 | 13.87 |
| 快速通道（simple_fact） | 27 | 5.73 | 5.96 | 6.34 | 6.49 | 4.11 | 6.85 |
| 复杂路径（formatter/unknown） | 13 | 8.60 | 8.42 | 10.82 | 12.16 | 3.26 | 13.87 |

### 5.3 关键阶段基准（秒）

| 阶段 | 平均 | P50 | P95 | 说明 |
| --- | ---- | ---- | ---- | --- |
| 混合检索 | 0.07 | 0.08 | 0.10 | Milvus+BM25 本地、含缓存，**不是瓶颈** |
| 意图路由 | 1.26 | 1.43 | 1.77 | LLM 调用；强信号规则命中时为 0 |

### 5.4 瓶颈定位

实测明确指向 **LLM 调用是绝对瓶颈，检索仅约 0.07s（约占 1%）**：

- 快速通道（平均 5.73s）≈ 检索 0.07s + 路由 1.26s + 答案生成约 4.4s，两次 LLM 串行（路由 + 生成）。
- 复杂路径（平均 8.6s）≈ 路由 + Agent 工具循环生成 + 合规审核，约三次 LLM 串行。
- 方案 A（快速通道改用 LLM 分类）提升意图准确率的代价，是快速通道增加约 1.26s 的串行路由。

明细数据：`data/eval/latency_benchmark.json`；测试脚本：`scripts/eval_latency.py`。

## 六、流式输出改造（2026-09-27）

非流式模式下，答案生成的约 4 秒内用户面对静止等待。改为流式后，首 token 到达即开始逐字渲染，显著降低主观等待感（总时长不变，考核口径从“总时长”转为“首 token 时间 TTFB”）。

| 路径 | 流式机制 | 实测 token 帧 |
| --- | --- | --- |
| 寒暄 greeting | SSE 层短路改为 `chat_stream_async` 逐 token | 13 帧 |
| 快速通道 simple_fact | 节点改为 `chat_stream` 逐 token 写入队列 | 79 帧 |
| 复杂路径 | 领域 Agent `answer_stream` 逐 token（原有） | 逐 token |
| 语义缓存命中 | 整段秒回 result（合理，不流式） | 0 帧，约 0.3s |

统一经 SSE 端点 `/api/v1/chat/stream`（text/event-stream）推送 stage/token/result/done 帧；TTFB 在首个 token/result 帧打点，stage/info 秒回帧不计入 TTFB，避免假首字。

流式后的目标口径：首 token TTFB P50 < 1.5s、P95 < 3s（寒暄实测约 3.1s，快速通道正常约 0.7–2s，受 DeepSeek 外部排队影响有长尾）；总时长不变，缓存命中约 0.3s。

## 七、冷启动治理（2026-09-27）

### 7.1 根因逐层下钻（真实归因）

首次请求一度测出 18–21s，逐层分解排除：

1. 不是建 Milvus 集合：集合已存在时仅 0.02s。
2. 不是模型权重构造：`SentenceTransformer(path, device=cpu)` 仅 0.21s。
3. 不是文件 IO、不是 CUDA 探测（设 `CUDA_VISIBLE_DEVICES=-1` 后）。
4. **真正根因：重型 ML 依赖的进程级一次性 import 成本**——transformers 5.37s + torch 2.92s + sklearn 2.24s ≈ 11s（`import sentence_transformers` 实测 12.04s）。该成本算法无法消除，只能移出用户请求路径。

### 7.2 治理措施（三道）

1. **启动后台预热**：应用 lifespan 在后台线程实例化检索器并做一次 dummy 编码，触发全部慢 import 与权重加载，不阻塞启动。
2. **就绪探针**：`/health/ready` 在嵌入模型未加载完时返回 503、加载完返回 200，负载均衡/部署等就绪后再打入流量，冷启动不落在真实用户；配合滚动发布，发布与扩容过程用户全程无感。
3. **单次加载保证**：Python import 锁 + 给嵌入模型加载加双检锁（`threading.Lock`），即使预热窗口内有请求，也等待同一次加载结果，不重复触发。

### 7.3 设备策略

`.env` 配置 `EMBED_DEVICE=cpu`（默认）：在 import torch 前设置 `CUDA_VISIBLE_DEVICES=-1`，跳过 Windows 上极慢的 CUDA 驱动探测；有 GPU 时改为 `cuda` 即可恢复设备探测。

需要说明：系统稳态长期运行时，普通用户并不会碰到冷启动；上述治理针对的是发布、扩容、崩溃恢复、多 worker 等“新进程诞生”的时刻。

## 八、优化历程完整对比（全量 105 条）

下表保留各轮演进以便追溯；**当前权威结果以第一章为准**。

| 指标 | 初始基线 | 第一轮（意图 5 项 + 延迟 5 项） | 第二轮（检索参数 + 方案 A） | 第三轮（父子分块 + 评测修正） | 最新复跑 |
| --- | --- | --- | --- | --- | --- |
| 证据覆盖率 | 95.9% | 95.9% | 98.0% | 99.0% | **99.0%** |
| chunk 信息命中率 | 67.3% | 67.3% | 68.4%（旧方法） | 98.0%（jieba 词级） | **98.0%** |
| 路径结构一致率 | 83.3% | 83.3% | 83.3% | 83.3% | **83.3%** |
| 图谱触发率 | 46.7% | 46.7% | 46.7% | 45.7% | **45.7%** |
| 全链路意图准确率 | 61.9% | 61.9% | 88.6% | 89.5% | **88.6%** |
| 合规通过率 | 95.2% | 95.2% | 95.2% | 94.3% | **96.2%** |

各轮主要工作：

- **第一轮**：意图侧加入对话上下文传入路由、意图-检索一致性校验、思维链推理、动态 few-shot（从 Golden QA 检索最相似案例）、规则混合仲裁；延迟侧加入工具循环提前终止、并行工具调用、低风险跳过 LLM 审核、重写次数 2→1、扩大快速通道。期间修复三个 bug：动态 few-shot 使用了 Python 不支持的 `\p{P}` 转义；提示词 `.format()` 把 JSON 示例花括号误当占位符（改 `.replace()`）；在线意图准确率一度仅 23.3%，根因是快速通道意图字段为空（修复为寒暄置 chitchat、简单事实走规则兜底）。
- **API 切换**：阿里云百炼 qwen-flash 免费额度耗尽（HTTP 403），切换 DeepSeek 官方接口；Gemini 因国内网络不通超时放弃。
- **工具扩展**：工具由 4 个扩到 **10 个**，新增账户余额、交易明细、信用卡、贷款、资产总览、理财订单六类只读查询；每个查询函数注释标注“生产环境对接对应业务系统 API”。系统不联网搜索他行产品（外网搜索类已实现但默认不注册、不开放），可提供本行产品的购买建议与适当性校验。
- **第二轮**：检索参数调优（chunk_size 350→200、overlap 70→80、top_k 5→8、MMR λ 0.5→0.7）；方案 A 把快速通道从规则兜底改为 LLM 精细分类，全链路意图准确率 61.9%→88.6%。
- **第三轮**：父子文档分块实际落地并全量重建索引（213 父 + 252 子 = 465 块）；同时修正评测方法，chunk 命中率口径还原为 98%，并经 A/B 实测如实确认父子分块对命中率的边际贡献为 0pp。
- **最新复跑（2026-09-27）**：离线四项全部持平；全链路意图 89.5%→88.6%（-0.9pp，判定为 LLM 正常抖动、非回归）；合规 94.3%→96.2%（+1.9pp）。

每条 Golden 标注问题、期望意图、参考文档 evidence、期望图谱路径 path、是否需风险提示 risk_required、复杂度等。数据集另含：对抗样本（g086–g090，诱导错误确认/编造/绕过适当性/索要敏感信息）、超纲样本（g091–g094，个股/加密货币/法律文书/市场预测）、模糊与半模糊样本（g095–g097）、多产品对比（g098–g100）。

设计约定：线上 badcase 提升为 Golden 时 **evidence 故意留空**，因为 badcase 的成因常常正是“检索错了”，自动填入当轮召回来源等于把 bug 固化成标准答案；evidence 必须人工补齐。手写样本用 g 系列编号、badcase 提升样本用 bc 系列，同一 trace 重复提升不追加新行（幂等）。

## 十一、后续优化方向

1. **路由与生成并行**：快速通道路由只用于标注意图、不参与检索决策，可与“检索 + 生成”并行后合并，预计快速通道再省约 1.2s。
2. **首 token 超时切换备用模型**：DeepSeek 作为单一外部 LLM，首 token 长尾不可控，超时后自动切备用端点。
3. **路由结果缓存、限制生成 max_tokens、精简提示词**：进一步缩短生成耗时。
4. **复杂路径审核并行化**：减少串行 LLM 环节。
5. **答案质量 LLM-as-Judge**：当前在线评测以意图与合规为主，答案质量评分已预留、默认未开启。
6. **标注数据清洗**：拆分 chitchat 中混杂的超纲/模糊/隐私边界样本，使意图准确率更真实。
7. **知识库文件监听**：安装 watchdog 后启用文档变更的自动增量入库（当前以启动扫描 + 手动/接口触发为主）。
8. **微调专用分类模型**：用 Golden QA 微调轻量分类模型，目标准确率 90%+、延迟 <100ms。

## 十二、检索层专项评测（2026-10）

本章针对检索层做更细粒度的评测，使用自动生成的 QA 评测集（`scripts/eval_qa.jsonl`，56 条，从知识库 chunk 自动生成问题），口径为 chunk 级严格匹配（golden_chunk_ids 与检索结果 chunk_id 归一化后比对）。

### 12.1 chunk 级匹配口径修复

**问题发现**：初始 chunk 级 Recall@5 仅 42.9%，远低于 evidence 级的 92.4%。逐层排查发现是评测脚本口径 bug——评测集 golden_chunk_ids 用文档级 ID（不带 `_c` 后缀），检索结果用 chunk 级 ID（带 `_cN` 后缀），严格匹配导致同一文档的其他 chunk 永远匹配不上，产生大量假阴性。

**修复**：`scripts/eval_retrieval.py` 的 `chunk_key()` 函数和 golden 处理都加 `re.sub(r"_c\d+$", "", cid)` 归一化为文档级 ID。同一文档的任意 chunk 命中即算对。

**修复前后对比**：

| 指标 | 修复前（bug） | 修复后 | 变化 |
|------|---------------|--------|------|
| Recall@5 | 42.9% | **82.1%** | +39.2pp |
| MRR | 0.316 | **0.655** | +0.339 |

> 说明：这是评测方法的修正，不是检索能力的飞跃。修复后 chunk 级与 evidence 级（92.4%）仍有差距，因为 chunk 级要求具体段落命中，比文档级更严格。剩余差距主要来自含指代的多轮问题（无上下文时检索不准）。

### 12.2 Query Rewriting 评测

**背景**：多轮对话中用户常说"这个基金的收益怎么算"、"它的风险等级呢"，直接检索会因为缺少实体而召回不准。项目实现了 `src/core/query_rewriter.py`（规则层零延迟 + LLM 层可选），在检索前将指代补全为具体产品名。

**评测方法**：`scripts/eval_retrieval.py --with-rewrite`，为 17 条含指代问题手动标注 `context_product`（模拟上一轮对话提到的产品名），对比改写前后的召回率。

**结果（17 条含指代问题）**：

| 指标 | 改写前 | 改写后 | 变化 |
|------|--------|--------|------|
| Recall@1 | 35.3% | 23.5% | -11.8pp |
| Recall@3 | 41.2% | 58.8% | **+17.6pp** |
| Recall@5 | 52.9% | 70.6% | **+17.6pp** |
| MRR | 0.4088 | 0.4255 | +0.0167 |

- 改写后提升命中：**4 条**（原未命中→改写后命中）
- 改写后降低命中：**1 条**（原命中→改写后未命中）
- 全量 56 条（带改写）：Recall@5 = **87.5%**，MRR = **0.6595**

> 说明：Recall@1 下降是因为改写后问题更具体，虽然 top5 内能命中，但排名可能靠后；Recall@3/5 提升明显，说明改写有效扩大了召回覆盖。规则层零延迟，不增加 LLM 调用。

### 12.3 多问题拆分（Decompose）评测

**背景**：用户一次问多个问题（如"存款保险保什么？理财受存款保险保障吗？"）时，单路检索可能只覆盖其中一个子问题的相关文档。项目实现了 `src/core/query_decomposer.py`，用 LLM 将多问题拆成独立子问题，并行检索后合并去重。

**拆分准确率（5 个用例）**：

| 用例类型 | 原问题 | 拆分结果 |
|---------|--------|---------|
| 单问题 | 稳盈添利30天的收益是多少？ | 1个（快速路径，不调LLM） |
| 三连问 | 这个基金的收益怎么算？风险大吗？适合我买吗？ | 3个 ✓ |
| 两连问 | 存款保险保什么？理财受存款保险保障吗？ | 2个 ✓ |
| 带连接词 | 我想买这个产品，需要满足什么条件？还有赎回规则是什么？ | 2个（补全指代）✓ |

**检索覆盖度提升（3 个多问题用例）**：

| 问题 | 不拆分 | 拆分后 | 新增 |
|------|--------|--------|------|
| 存款保险+理财保障 | 9 chunk / 7 来源 | 13 chunk / 10 来源 | +4 / +3 |
| 稳盈添利收益+风险 | 8 chunk / 5 来源 | 14 chunk / 8 来源 | +8 / +3 |
| 大额存单利率+提前支取 | 8 chunk / 3 来源 | 10 chunk / 5 来源 | +2 / +2 |
| **平均** | **8.3 / 5** | **12.3 / 7.7** | **+4.7 / +2.7** |

> 设计取舍：不新增 LangGraph 节点，拆分逻辑内聚在 `route_retrieve_node` 内部，下游零改动。路由仍用原始 query（意图分类需要完整语境），检索用拆分后的子问题。单问题走快速路径不调 LLM，零额外延迟。LLM 拆分失败时降级为单问题检索，不阻断主流程。

### 12.4 检索层评测脚本

| 参数 | 用途 |
