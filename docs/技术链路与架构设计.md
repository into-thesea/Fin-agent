# Fin-Agent 智能客服系统技术链路文档

> 版本：kb-governance 分支（2026-10-05）
> 覆盖：意图识别、查询改写、RAG 检索、LangGraph 编排、快速通道、问题与解决方案

---

## 一、系统层次总览

Fin-Agent 采用五层架构，自底向上：

```
┌─────────────────────────────────────────────────┐
│  ⑤ 输出层：格式化 + 来源标注 + 转人工工单          │
├─────────────────────────────────────────────────┤
│  ④ 审核层：Reviewer 反幻觉 + 重试循环             │
├─────────────────────────────────────────────────┤
│  ③ 生成层：领域 Agent（理财/闲聊/通用）           │
├─────────────────────────────────────────────────┤
│  ② 检索层：混合检索（向量+BM25）+ RRF + 精排      │
├─────────────────────────────────────────────────┤
│  ① 理解层：意图识别 + 查询改写 + 槽位填充         │
└─────────────────────────────────────────────────┘
         ↑ LangGraph 编排所有节点的流转与条件路由
```

各层职责：
- **理解层**：判断用户意图（12 类业务意图+unknown）、补全指代、扩展产品别名、填充槽位
- **检索层**：从知识库召回相关文档，供生成层引用
- **生成层**：根据意图路由到对应 Agent，基于检索证据生成回答
- **审核层**：事实核查、禁语检查、PII 检测，不通过则注入反馈重生成
- **输出层**：统一格式、标注来源、触发转人工

## 二、意图识别层

### 2.1 技术选型

| 维度 | 选型 | 理由 |
|---|---|---|
| 模型 | DeepSeek-chat（API） | 成本低、中文理解好、响应快 |
| 分类方式 | LLM 提示词分类（非微调） | 12 类意图用提示词即可达到 88%+，微调成本高且迭代慢 |
| 输出结构 | 两层 JSON（大类 + 小类 + 置信度 + 推理链） | 大类做粗路由，小类做精处理，推理链可审计 |
| 兜底 | 强信号规则直出 + 关键词规则兜底 | LLM 不可用时降级，保证不崩 |

### 2.2 层级意图体系

将原扁平 12 类重构为两层：

**第一层（4 大类）：**
- `product_info` 产品咨询类
- `return_risk` 收益风险类
- `transaction` 交易操作类
- `service_safety` 服务安全类

**第二层（12 小类）：**

| 大类 | 小类 | 说明 |
|---|---|---|
| product_info | product_consult | 单产品属性咨询 |
| product_info | product_compare | 多产品对比/推荐 |
| product_info | deposit_insurance | 存款保险保障 |
| return_risk | income_question | 收益/利率/保本 |
| return_risk | risk_suitability | 风险等级/适当性 |
| transaction | buy_process | 购买流程/门槛 |
| transaction | hold_redeem | 持有/赎回/到期 |
| transaction | fee_rule | 费率/手续费 |
| service_safety | fraud_report | 诈骗/飞单举报 |
| service_safety | complaint | 投诉 |
| service_safety | service_policy | 客服规则/隐私 |
| service_safety | chitchat | 闲聊/领域外 |
| — | unknown | 兜底（不归类） |

### 2.3 分类流程

```
用户问题
  │
  ├─ 强信号规则命中？──是──→ 直出意图（fraud_report/complaint/deposit_insurance），不调 LLM
  │
  └─ 否
      │
      ├─ 续轮意图继承命中？──是──→ 沿用上一轮意图，不调 LLM
      │
      └─ 否
          │
          └─ LLM 调用（一次调用输出大类+小类）
              │
              ├─ 校验：小类必须属于返回的大类？
              │   ├─ 是 → 使用结果
              │   └─ 否 → 以小类反查大类兜底（不增加调用次数）
              │
              └─ LLM 失败/超时 → 关键词规则兜底（12 类关键词匹配）
```

### 2.4 关键参数

- 提示词：`INTENT_DETECTION_PROMPT`，包含 4 大类定义、12 小类定义与例句、输出 JSON 格式
- few-shot：`use_few_shot` 参数控制，默认 `True`（线上行为），评测时传 `False` 避免数据泄漏。few-shot 是指在提示词里给几个"问题→意图"的示例，让模型照着分类；但如果示例来自评测集本身，模型等于提前看到了答案
- 强信号规则：`_STRONG_SIGNAL_INTENTS` = {fraud_report, complaint, deposit_insurance}，命中即直出
- 规则兜底关键词：12 类各有一组关键词，按优先级匹配
- 延迟：单轮路由 P50 ~1.6s，P95 ~2.0s（含 LLM 调用）

### 2.5 评测结果（干净口径，few-shot 关闭）

| 指标 | Dev 集（105条） | 测试集（40条 held-out） |
|---|---|---|
| 总体准确率 | 88.6% | 92.5% |
| 规则直出占比 | 20% | 7.5% |
| 10/12 意图 | 100% | 100% |
| 最弱意图 | chitchat 62.5% | chitchat 60% |

> **held-out 测试集**：开发全程没有碰过、没有用来调提示词的独立问题集。Dev 集在反复调参中已被模型"见过"，准确率会偏高；测试集模拟真实用户的陌生提问，数字更可信。

## 三、查询改写层

查询改写在路由之前执行，纯规则、零 LLM、零编造，分两步：

### 3.1 指代补全（多轮上下文）

**目的**：把"它""这个产品"等指代替换为上一轮的焦点产品名。（指代消解：识别用户说的代词指的是哪个具体事物，这里只处理产品指代）

**规则**：
1. 从会话状态的持久化槽位中取 `product`（焦点产品）。槽位（slot）是对话系统中存储关键信息的字段，如产品名、金额、风险等级，跨轮保留
2. 如果当前问题含指代近指词（`它`、`这个产品`、`这款`、`它们` 等 12 个词）且不含产品名，则替换
3. 无历史 / 无焦点产品 / 已含产品名 / 不含指代词 → 原样返回

**示例**：
```
轮1: "稳盈添利30天的收益怎么样？" → 不变
轮2: "那它的风险等级呢？" → "那稳盈添利30天的风险等级呢？"
轮3: "它保本吗？" → "稳盈添利30天保本吗？"
```

### 3.2 产品别名扩展

**目的**：把用户口语叫法替换为知识库规范产品名，提升检索精确匹配。

**规则**：
1. 构建别名→规范名反向映射（24 款产品，每款 2-5 个口语别名），按别名长度降序排列
2. 最长优先匹配（避免"国债"误替换"记账式国债10年期"中已含规范名的部分）
3. 已含规范名时不重复替换
4. 纯规则，零 LLM

**别名表示例**：

| 规范名 | 口语别名 |
|---|---|
| 大额存单3年期 | 大额存单、3年大额存单、三年期大额存单 |
| 沪深300指数增强基金 | 沪深300、指数增强、300指数基金 |
| 康健无忧重大疾病保险 | 重疾险、康健无忧、康健无忧重疾 |
| 账户黄金(积存金) | 账户黄金、积存金、黄金积存 |

**设计原则**：只保留指向具体产品的简称/俗称，不用泛化品类词（如"国债""货币基金""混合基金"）——品类词会同时匹配多款产品，查询扩展时误替换反而缩小召回。

## 四、RAG 检索层

> **RAG（Retrieval-Augmented Generation，检索增强生成）**：先从知识库检索相关文档，再把文档作为上下文喂给 LLM 生成回答。核心价值是让 LLM 基于真实资料回答，减少幻觉，且知识库更新不需要重新训练模型。

### 4.1 技术选型

| 组件 | 选型 | 参数 | 简要说明 |
|---|---|---|---|
| 向量数据库 | Milvus（唯一后端，不降级 FAISS） | — | 专门存储向量的数据库，支持 ANN（近似最近邻）快速搜索，比暴力计算相似度快几个数量级 |
| 嵌入模型 | bge-base-zh-v1.5（本地离线加载） | 768 维，CPU 强制推理 | 把文本转成 768 维数字向量，语义相近的文本在向量空间中距离近 |
| 稀疏检索 | BM25（jieba 分词） | k1=1.5, b=0.75 | 经典关键词匹配算法，按词频和文档长度打分，弥补向量检索的关键词盲区（如产品名、数字） |
| 融合算法 | RRF（Reciprocal Rank Fusion） | k=60 | 把向量和 BM25 两路结果按排名合并：排名越靠前得分越高（score=1/(k+rank)），不依赖两路分数的绝对值可比 |
| 多样性重排 | MMR（Maximal Marginal Relevance） | λ=0.5，候选池 top_k×3 | 在相关性和多样性之间取平衡，避免 top_k 全是同一产品的相邻段落；λ 越大越看重相关性 |
| 精排器（可选） | gte-rerank-v2（API） | 候选池 20 → top_k 5 | 用更强的语义模型对候选逐条打分重排序，比 RRF 更准但多一次 API 调用 |
| 缓存 | Redis | 向量结果缓存 TTL=300s | 内存数据库，相同查询 5 分钟内直接返回缓存结果，跳过编码和搜索 |

### 4.2 检索详细流程

```
改写后的查询
  │
  ├─ 1. 向量检索（Path A）
  │   ├─ bge-base-zh-v1.5 编码查询 → 768 维向量
  │   ├─ Milvus ANN 搜索，取 top_k×3 候选（MMR 模式）或 top_k（非 MMR）
  │   ├─ MMR 多样性重排：λ×相关性 - (1-λ)×与已选最大相似度
  │   └─ Redis 缓存命中则跳过编码与搜索
  │
  ├─ 2. BM25 稀疏检索（Path B）
  │   ├─ jieba 分词 → BM25 评分（按词频和文档长度算分，纯关键词匹配）
  │   ├─ 取 top_k×3 候选
  │   └─ 金丝雀探针：启动时用"存款保险"这个已知必命中的查询验证索引健康，失败则响亮报错（类似煤矿里的金丝雀，先死说明环境有毒）
  │
  ├─ 3. RRF 融合
  │   ├─ 对两路结果按排名计算 RRF 分数：score = Σ 1/(k + rank)，排名第1得1/61，排名第2得1/62...
  │   ├─ 按融合分排序，取 rerank_pool（默认 20）条
  │   └─ 两路都必须有结果；稀疏路为空时直接报错（不静默降级为纯向量）
  │
  ├─ 4. 精排（可选，配置开启时）
  │   ├─ gte-rerank-v2 对 20 条候选逐条计算"查询-文档"语义相似度，重排序
  │   ├─ 收敛到 top_k（默认 5）
  │   └─ 精排失败时保留 RRF 原序，不影响可用性
  │
  └─ 5. 父子文档还原
      ├─ 原理：知识库按"父块（章节完整内容）+ 子块（句子级检索单元）"两级切分
      │   检索时用子块（细粒度，召回更准），命中后通过 parent_id 找到对应的父块
      └─ 把父块的完整章节内容注入提示词（避免只给模型一句话导致断章取义）
```

### 4.3 检索阶段做的优化

**1. 强制 CPU 离线加载嵌入模型**
- 问题：Windows 首次 `torch.cuda.is_available()` 探测 CUDA 驱动耗时 14s+
- 解决：import torch 前设 `CUDA_VISIBLE_DEVICES=-1`，bge 冷启动降到 ~0.3s
- 配置：`.env` 设 `EMBED_DEVICE=cpu`（默认），需要 GPU 时改为 `cuda`

**2. 全局单例 + 双检锁**
- `HybridRetriever` 用 `__new__` 实现单例，避免重复加载索引和模型
- 嵌入模型用 `threading.Lock` 双检锁，预热与早期请求不重复加载

**3. Redis 缓存层**
- 向量检索结果按 `embedding_hash + top_k` 缓存，TTL 300s
- 缓存失效只影响速度，不影响答案（可降级）

**4. BM25 金丝雀探针**
- 问题：稠密路（ANN）永远返回 k 个最近邻，"稠密有条 + 稀疏 0 条"有歧义——既可能是 BM25 挂了，也可能是查询离题
- 解决：索引加载后用"存款保险"做一次探针，结果挂在索引对象上，只验一次
- 探针失败时响亮报错，避免"假混合检索"（实际只有向量路在工作）

**5. 不静默降级**
- Milvus 不可用时不降级 FAISS（两种后端答案不同，FAISS 路径上传的新文档进不去 Milvus，会导致检索不完整）
- BM25 索引不存在时直接报错，不退化为纯向量
- 精排失败时保留 RRF 原序（只影响排序质量，不影响可用性）

**6. MMR 多样性重排**
- 问题：向量检索 top_k 容易返回语义高度重复的 chunk（同一产品的相邻段落）
- 解决：先取 top_k×3 候选，再用 MMR 选 top_k，λ=0.5 平衡相关性与多样性
- 配置：`mmr_enabled=true`，`mmr_lambda=0.5`（可编辑配置热更新）

**7. 父子文档分块**
- 原理：一篇文档先切成章节级父块（保留完整上下文），再把每个父块按句子切成子块（细粒度检索单元），子块携带 parent_id 指向父块
- 检索用子块（细粒度，提高召回精度），生成用父块（完整上下文，减少断章取义）
- parent_id 映射懒加载，首次检索时构建

### 4.4 遇到的问题与解决方案

| 问题 | 现象 | 解决方案 |
|---|---|---|
| 假混合检索 | BM25 索引坏了但系统不报错，实际只有向量路在工作，召回率下降 | 金丝雀探针 + 不静默降级，稀疏路为空时响亮报错 |
| CUDA 探测拖慢启动 | 首次请求延迟 14s+ | 强制 CPU 离线加载，`CUDA_VISIBLE_DEVICES=-1` |
| 向量检索结果重复 | top_k 全是同一产品的相邻段落 | MMR 多样性重排，候选池扩大 3 倍 |
| 产品名不匹配 | 用户说"大额存单"，知识库叫"大额存单3年期"，检索命中低 | 产品别名扩展，24 款产品每款 2-5 个口语别名 |
| 泛化品类词误替换 | 用"国债"做别名会同时匹配储蓄国债和记账式国债，缩小召回 | 别名表只用指向具体产品的简称，不用品类词 |
| FAISS/Milvus 答案不一致 | 降级 FAISS 后新文档检索不到 | 移除 FAISS 降级，Milvus 不可用时直接报错 |

## 五、LangGraph 编排层

### 5.1 节点清单

| 节点 | 职责 |
|---|---|
| `classify_node` | greeting/complex 二分（纯规则，<0.1ms） |
| `memory_node` | 路由前注入分层记忆（用户画像/历史偏好） |
| `greeting_node` | 问候/闲聊轻量回答（无检索） |
| `route_retrieve_node` | 意图识别 + 检索 + 续轮继承 + 一致性校验 |
| `simple_fact_node` | 快速通道（五道闸通过，直接用检索证据生成） |
| `unknown_node` | unknown 兜底回答 |
| `slot_check_node` | 槽位检查（缺槽位则追问，不进生成） |
| `orchestrator_node` | 按意图派发到领域节点 |
| `finance_node` | 理财知识库问答（7 类信息意图） |
| `chitchat_node` | 闲聊/领域外回答 |
| `general_node` | 通用兜底 |
| `handoff_node` | 确定性转人工（诈骗/投诉） |
| `subscribe_node` | 申购门控（适当性校验 + 短信验证码） |
| `reviewer_node` | 反幻觉审核（QuickCheck + LLM 复核） |
| `regenerate_node` | 注入审核反馈重新生成 |
| `formatter_node` | 格式化输出 + 来源标注 |

### 5.2 图拓扑

```
START
  │
  ▼
classify_node ──→ memory_node
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
     greeting_node      route_retrieve_node
          │                   │
         END       ┌──────────┼──────────┐
                   ▼          ▼          ▼
            simple_fact  unknown_node  slot_check
                   │          │          │
                  END        END    ┌────┴────┐
                                    ▼         │
                              orchestrator   END
                                    │
                    ┌───────────┬───┴───┬───────────┐
                    ▼           ▼       ▼           ▼
              finance_node  chitchat  handoff   subscribe
                    │           │       │           │
                    └───────────┴───┬───┴───────────┘
                                    ▼
                              reviewer_node
                                    │
                          ┌─────────┴─────────┐
                          ▼                   ▼
                   regenerate_node      formatter_node
                          │                   │
                          └────→ reviewer    END
```

### 5.3 关键条件路由

**`route_retrieve_node` 内部流程**（核心节点）：
1. 多问题拆分（单问题快速路径直接返回 `[原问题]`，零额外延迟）
2. 路由与检索并发（线程池，路由 + N 个检索，上限 6 线程）：路由 LLM 调用和检索同时跑，不用等路由出结果再检索，总延迟取两者中较慢的那个而非相加
3. 续轮意图继承：命中则跳过路由 LLM，沿用上一轮意图
4. 强信号规则：fraud_report/complaint/deposit_insurance 直出
5. LLM 路由：输出两层意图（大类+小类），校验一致性
6. 意图-检索一致性校验：检索 top1 分数 <0.60 时调整意图
7. 补齐大类：所有路径产出意图时同步写 `category` 字段

**`orchestrator_node` 派发逻辑**：
- `INTENT_NODE_MAP` 映射 12 类意图到处理节点
- 7 类信息意图 → `finance_node`（走知识库）
- fraud_report/complaint → `handoff_node`（确定性转人工）
- chitchat → `chitchat_node`
- unknown → `general_node`
- buy_process 且金额已填 → `subscribe_node`（申购门控）

**`reviewer_node` 跳过 LLM 复核的条件**（满足任一）：
- QuickCheck 通过（数字/来源可接地）
- 确定性节点（转人工/申购门控）
- 低风险意图：chitchat / service_policy / unknown（不存在收益承诺等高危幻觉）

### 5.4 状态管理

- `CsState` TypedDict 承载全链路状态：query、intent、category、confidence、contexts、slots、entities、agent_result、review、retry_count、stage 等。（TypedDict 是 Python 的类型化字典，规定每个字段的名称和类型，LangGraph 用它在节点间传递数据）
- `MemorySaver` 做检查点，支持会话级状态持久化（把每轮的状态存下来，下一轮可以接着用，实现多轮对话记忆）
- 续轮继承依赖 `last_intent` 和 `awaiting_slot` 字段，`_empty_state` 初始化时读取

## 六、快速通道（Fast Path）

### 6.1 四道闸串联

快速通道让简单问题跳过完整 Agent 管道，直接用检索证据生成答案，降低延迟。

```
查询 → 闸① HANDOFF 检查 → 闸② 私有数据检查 → 闸③ 信息意图检查 → 闸④ KB 证据检查 → 快答
```

| 闸 | 检查内容 | 不通过则 |
|---|---|---|
| ① HANDOFF | strong_intent 是否为 fraud_report/complaint | 走完整管道（转人工） |
| ② 私有数据 | 查询是否含"我的/持仓/查一下"等私有数据标记 | 走完整管道（需用户状态） |
| ③ 信息意图 | intent 是否在 7 类信息意图集合中 | 走完整管道 |
| ④ KB 证据 | 检索 top1 融合分是否 ≥ 0.60 | 走完整管道（证据不足） |

### 6.2 关键设计决策

**移除置信度阈值闸**：
- 实测 router 自报 confidence 饱和在 0.95（105 条 golden 里 93% 在 0.95 以上），0.95 档里错 6 条、低于 0.95 的 4 条里错 3 条——方向对但没区分度
- 阈值从 0.70 扫到 0.98，结果几乎不变
- 全链路实测：关闭 = 0.905、T=0.90 = 0.895，差 1.0pp 落在 ±2pp 抖动带内
- 结论：整道闸移除，不留恒真开关。有区分度的是检索 top1 分数（<0.60 区间意图错 37.5%，≥0.70 为 0）

**greeting 硬前置**：
- greeting 优先判定（整句 ≤12 字且含问候词），不查 KB、不需意图，不受其他闸影响
- 含私有数据措辞一律强制走完整管道

## 七、意图继承（多轮）

### 7.1 规则式继承（零 LLM）

`intent_inheritance.py` 实现四条继承规则 + 话题切换检测：

| 规则 | 触发条件 | 行为 |
|---|---|---|
| 验证码续轮 | 命中 6 位数字码 + 上一轮 buy_process | 继承 buy_process |
| 确认词 | "对/是的/好的/确认" + 上一轮在流程意图中 | 继承上一轮意图 |
| 纯金额 | "50万/10万" + 上一轮 buy_process | 继承 buy_process |
| 短问法 | 查询 <10 字 + 上一轮在流程意图中 + 无话题切换词 | 继承上一轮意图 |
| 话题切换 | 含"本金/保本/靠谱/风险/投诉/转人工"等 22 词 | 不继承，重新路由 |

### 7.2 效果

- 继承命中时跳过路由 LLM，单轮延迟从 ~1.6s 降到 <0.1s
- 30 会话评测中续轮准确率 76.5%（与扁平版持平）
- 已知弱点：比较上下文中的短问句（"风险呢？"）未继承 product_compare，仍按字面分类

## 八、审核层（Reviewer）

### 8.1 两级审核

**QuickCheck（纯规则，零 LLM）**：
- 禁语检查（保本/稳赚/无风险等承诺性用语）
- PII 检测（身份证号/银行卡号/手机号，PII=个人身份信息，泄露会合规违规）
- 数字可接地检查（回答中的数字是否在检索证据中出现）
- 来源覆盖检查（回答引用的产品是否在检索结果中）

**LLM 复核（可选，高风险意图才调）**：
- 逐条断言检查：每个事实声明是否有检索证据支撑
- 输出 verdict（pass/reject）+ 未支撑断言列表
- reject 时注入反馈重新生成（最多重试 1 次）

### 8.2 跳过 LLM 复核的场景

- QuickCheck 通过
- 确定性转人工/申购门控
- 低风险意图（chitchat/service_policy/unknown）

## 九、评测体系

### 9.1 评测集

| 数据集 | 规模 | 用途 |
|---|---|---|
| finance_qa_golden.jsonl | 105 条 | Dev 集（调提示词用） |
| finance_qa_test.jsonl | 40 条 | Held-out 测试集（全程未碰，最终数字） |
| finance_sessions.jsonl | 30 会话 67 轮 | 多轮评测 |
| finance_sessions_6x3.jsonl | 6 会话 18 轮 | 精简多轮（省 token） |

### 9.2 评测指标

| 指标 | 说明 |
|---|---|
| 单轮意图准确率 | 标注意图 vs 模型预测 |
| 多轮意图准确率 | 含上下文的连续对话 |
| 续轮准确率 | 需上下文的轮次（needs_context=true） |
| 合规通过率 | 诈骗/投诉是否正确转人工、是否有禁语 |
| 指代消解成功率 | "它"是否正确替换为产品名 |
| 延迟 | P50/P95，分路由延迟和端到端延迟 |

### 9.3 防泄漏机制

- few-shot 示例库与评测集物理隔离（评测时 `use_few_shot=False`）
- 提示词静态例句与 Golden QA 零重合（全部独立构造）
- 测试集全程不用于调参，跑完即封存
- bigram 去泄漏检查：测试集与 dev 集+提示词例句的字符 bigram 重叠度 >50% 则改写。bigram 是连续两个字的组合（如"大额"、"额存"），重叠度高说明两句话措辞太像，模型可能靠记忆而非理解答对

## 十、已知弱点与后续方向

| 弱点 | 表现 | 根因 | 方向 |
|---|---|---|---|
| 无上下文模糊问题 | "收益怎么样？"判 income_question 而非 chitchat | 模型倾向按字面分类，不识别缺上下文 | 提示词加"无明确产品名归 chitchat"规则 |
| 多轮短问句继承 | "风险呢？"在比较上下文中判 product_consult | 继承规则只覆盖流程意图（buy/hold），未覆盖 compare | 扩展继承规则到比较意图 |
| 比较风险归类 | "A和B哪个风险高"判 income_question 而非 product_compare | 风险关键词触发收益风险类 | 提示词强调"比较两个产品归 product_compare" |
| 端到端延迟 | 多轮平均 7.7s/轮 | 检索+生成+审核串行 3 次 LLM 调用 | 审核跳过率提升、生成流式输出 |
