# 数据清洗与文档切分入库 · 细节问题与处理

> 记录日期：2026-10-11
> 背景：本文档记录「知识数据从 PDF / Markdown 进来，到切分成可检索的块、写进 Milvus 与 BM25、并同步图谱」这条链路上的设计取舍与踩坑。与《意图识别与延迟优化方案》并列，同属模块级复盘。
> 当前规模：分块文件 1942 行 = 417 父块 + 1525 子块（内置 465 行 / 上传 1477 行）；Milvus 1525 条子块，BM25 1525 条。

---

## 一、链路全貌

这条链路有两个入口，**产物一律不许手写**，只能由构建脚本从事实源派生。

### 入口 A：内置知识库

```
data/finance_kb/*.md ──┐
catalog.jsonl         ├─→ build_finance_kb.collect_chunks()  → ## 分节
kg_domain_triples.jsonl┘                                     ↓
                            build_parent_child_chunks()  ── 父块 + 子块
                                        ↓
              rebuild_local(): chunks_processed.jsonl + BM25
              render_kg_triples(): kg_triples.jsonl
              load_vector_index(): Milvus
```

触发点有两个，**行为不一样**（见第五节坑 3）：

- 文件监听（`src/api/main.py` 的 `_start_kb_watcher`）：`data/finance_kb/` 有变化 → 防抖 5 秒 → `sync_kb.main()`，走全链路（构建 → 三方计数校验 → 灌图 → 回归 → 记账）。
- 管理台「重建知识库」按钮：`kb_tasks.rebuild_kb_task` 只调 `build_all()`，**不经过 `sync_kb`**。

### 入口 B：上传文档（PDF / Markdown / TXT）

```
上传 → 内容哈希判重 → 占位登记(status=pending_review) → Celery preview_pipeline
      → smart_chunk_pdf() 解析+切分 → data/kb_pending/{doc_id}_chunks.jsonl
      ↓ 管理员在前端审核预览分块
approve_document(doc_id):
  Step1 覆盖写入 chunks_processed.jsonl
  Step2 add_chunks_to_index() → Milvus
  Step3 rebuild_bm25_index()  ← 从文件重建，所以 Step1 正确它就正确
  Step4 status=done
  Step5 失效缓存
  Step6 删临时分块文件
      ↓
（新增）派发 Celery extract_triples → 三元组进待审队列 → 人工通过 → 写源文件 → 收敛进 Neo4j
```

分块粒度、切分参数（`chunk_size` / `overlap` / `max_chunk_content`）走 `data/kb_settings.json`，改完免重启生效。注意三个参数的**生效范围不同**：章节路径上父块是整章不设限、子块只认 `max_chunk_content`（即 `CHILD_CHUNK_SIZE`，默认 150），`chunk_size` / `overlap` 只作用于无章节时的滑动窗口回退。

## 二、PDF 解析与切分策略

### 章节感知优先，滑动窗口兜底

`smart_chunk_pdf()` 分两步走：

1. **先试章节检测**（`_chaptered_chunk`）：从 PDF 文本里识别标题层级，构建章节树，按章节切。切出来的块**注入 `[章节标题]` 前缀**提升 embedding 区分度。实测样例：

   ```
   [产品概述] 产品概述
   产品名称 “聚宝财富专享8号1722期”人民币理财产品
   本产品在全国银行业理财信息登记系统的登记编码为 C1086817000067...
   ```

2. **检测不到标题就回退滑动窗口**（`_sliding_window_chunks`）：跨页按窗口切，**不做父子切分**（没有章节结构，父块无从谈起）。

这个「先试后兜底」的结构是有意的：理财产品说明书版式差异极大，硬要求章节结构会让一部分 PDF 直接抽不出东西。

### 长度分布（实测，1525 子块 / 417 父块）

| | 中位 | 均值 | 最长 |
|---|---|---|---|
| 父块 | 129 | 379 | 8744 |
| 子块 | 129 | 121 | **150（有上限）** |

**55%（228/417）的父块只有 ≤1 个子块** —— 章节本来就短（中位 129 字），切不出子块，父块和唯一的子块内容逐字相同。这个数据直接决定了父子分块的取舍，见下一节。

### 分块去重

内容完全相同的块只保留一份（按 `content_hash`）。典型场景：同一类产品的通用口径（如四只基金的「代销口径」）逐字相同，不去重会让检索返回四条一模一样的结果，挤占 top-k 且分数并列无法区分。

## 三、父子分块与检索的衔接

### 设计：子块入索引，父块只作上下文

```
子块(≤150 字, 带[章节标题]前缀) → 进 Milvus / BM25，参与向量与稀疏检索
    ↓ 命中
parent_id_of(chunk)  从 chunk_id 派生父块 id（形如 "{parent_id}_c{n}"）
    ↓
_load_parent_map()   从 chunks_processed.jsonl 取 chunk_type=="parent" 的行
    ↓
整章内容喂给 LLM
```

**父块内容来自本地分块文件，不来自 Milvus** —— 它从不参与"检索"，只参与"回答"。

### 为什么父块不该进索引（实测依据）

1. **55% 的父块与某个子块逐字相同**（章节太短没切开）。进索引就是成对的重复向量，一个查询命中会召回两条内容完全相同的结果。
2. **长父块会被 embedding 截断**：最长 8744 字，而 `bge-base-zh-v1.5` 上下文 512 token。截断后向量只代表开头一段——恰好是"整章语义"里最没代表性的部分。

两头都不划算：短的重了，长的失真了。所以目前 417 个父块全部**只存在于分块文件**，Milvus/BM25 里一个都没有。

### 代价（明确记录）

检索多了一个**本地文件依赖**：`chunks_processed.jsonl` 必须在。丢了的话 `_load_parent_map` 打一条 warning 返回空 → `_expand_to_parents` 原样保留子块——**降级但不报错**。

这是有意的取舍：用"多一个文件依赖"换"干净的向量空间"。如果将来要翻案（父块也进索引），必须**先跑评测**再定，不能拍脑袋。

## 四、入库的写入语义

### 分块文件是「覆盖」，不是「追加」

`approve_document` 的 Step 1 用 `_append_chunks_to_store(chunks, replace_doc_id=doc_id)`：**先清掉该文档已写入的行再写**。

键是 `pending_doc_id`（`preview_document` 打上的），**不是文件名** —— 两份同名文档各写各的，按文件名会互相误删。

### 向量侧同样覆盖

`add_chunks_to_index` 在插入前先 `delete_by_chunk_ids()` 清掉同 chunk_id 的旧行。Milvus 没有文件那样的"重写"语义，只能显式删。chunk_id 是内容派生的，同一份文档反复入库得到的 id 完全一致，所以它能精确圈定"这一次要覆盖的窗口"。

放在 `add_chunks_to_index` 内部而不是调用方，因为它是两条 ETL 路径（`ingest_document` / `approve_document`）的共同收口。

### 用户可见文案与产物字段

`pending_doc_id` 是**预览期**字段，但它现在会一直留在永久分块文件里（1477 行上传数据都带着它）。目前它承担着"文档身份"的作用（覆盖写的键）。这是个历史遗留的耦合，记在这里以免将来改预览格式时误删。

## 五、踩坑记录

按「现象 → 根因 → 修复 → 验证」写。**每一条都是实测出来的，不是读代码推的**。

### 坑 1：父子分块在检索侧整条空转

**现象**：父子分块做完之后，检索命中子块却永远拼不回父章节，LLM 拿到的是 150 字碎片。

**根因**：`_expand_to_parents` 读 `chunk["parent_id"]`，但**两条检索路都不透出这个字段**——Milvus collection 没建该列、`search()` 的 `output_fields` 不含它，BM25 的 payload 只存 id/text/source/section。于是 `parent_id` 恒为 None，展开函数永远走 else 分支。

**修复**：父块 id 不必再往索引里加——子块 id 形如 `{parent_id}_c{n}`，关系本来就写在 id 里。新增 `parent_id_of()` 从 chunk_id 派生，省掉改 Milvus schema + 清库全量重建。实测 1525 条子块派生结果与文件里的显式 `parent_id` 100% 一致。

**教训**：**"写好了但没接线"是这类系统里最高频的 bug 形态**。同一个毛病在这条链路上出现了三次（本坑、坑 3、三元组抽取器全仓无调用方）。

### 坑 2：父块口径三处不一致

**现象**：审核通过一份上传文档后，父块也被灌进了 Milvus/BM25。

**根因**：同一个判断被硬编码了三遍，第三遍忘了：

| 位置 | 是否过滤父块 |
|---|---|
| `vector_indexer.rebuild_vector_index`（全量重建） | ✅ 过滤 |
| `bm25_index.rebuild_bm25_index`（BM25 重建） | ✅ 过滤 |
| `vector_indexer.add_chunks_to_index`（增量） | ❌ **漏了** |

而 `smart_chunk_pdf` 是**产出**父块的。加上 `add_chunks_to_index` 有**两个**调用方（`ingest_document` 和 `approve_document`），两个都没过滤。

**修复**：判断抽成 `smart_chunk.indexable_chunks()` 一处定义，三处共用；过滤加在 `add_chunks_to_index` **内部**（收口处，一次修两个调用方）。

**验证**：给收口处喂父块+子块混合列表，打桩模型与 Milvus，断言只有子块被编码；**并验证测试有牙齿**——临时拆掉过滤 → 2 条红，装回 → 4 条绿。真上传也复验过：审核通过返回 `向量化: 51 条`（不是 65）。

**教训**：同一个判断写三遍，就一定会有第四遍漏掉。**收口比复制安全**。

### 坑 3：`verify()` 拿文件总行数去比只含子块的索引

**现象**：知识库同步（`sync_kb.py`）**每一次都在最后一步回滚**，manifest 从 2026-09-14 起再没更新过。

**根因**：父子分块重构后，分块文件里同时躺着父块和子块（1942 行），而 Milvus/BM25 按设计只有子块（1525 条）。`verify()` 却拿**文件总行数**去比 → `1942 ≠ 1525` → 判定"校验失败" → 回滚。

**后果**：整个自动化同步链路断了很久没人发现，图谱也跟着永远落后于源（Neo4j 少 24 条边），直到人工对账才暴露。

**修复**：`verify()` 先从文件里剔掉父块再同口径比对（新增 `_count_indexed()`）。注意**不是放宽阈值**，而是让两边数同一个集合——判据仍是严格相等。

**验证**：`indexable=1525(文件 1942 行, 父块 417 不入索引) milvus=1525 bm25=1525` → True。另外用 chunk_id 反查确认 Milvus 与文件子块**集合完全相同**（缺 0 多 0），不只是数量相等。

### 坑 4：Milvus 的删除是软删，计数会滞后

**现象**：删掉文档后，`sync_kb.verify()` 必然失败回滚。

**根因**：`MilvusManager.total_count` 读 `collection.num_entities`，而 Milvus 删除是软删，未 compaction 前**仍把已删行算在内**。实测删完两份文档后：`num_entities=1627`，而实际可查只剩 1525 → `verify` 得到 `indexable=1525 milvus=1627 bm25=1525` → False → 回滚。

也就是说：**任何人删过一个文档，下一次知识库同步都会失败**，跟具体删了谁无关。

**修复**：`total_count` 改用 `query(expr="id >= 0", output_fields=["count(*)"])`（会计入删除，同次实测返回 1525），不再用 `num_entities`。

**教训**：这个属性唯一的用途就是校验计数，所以**准确性比"便宜"重要**。任何时候想用 `num_entities` 做判断，先想想它是不是滞后值。

### 坑 5：审核入库失败后重试会重复追加

**现象**：一次 500 之后重试，同一份文档在分块文件里占了 130 行而不是 65 行。

**根因**：`approve_document` 文档里写的「要么全部成功，要么全部不入库」**只覆盖 `status`，不覆盖分块文件**。Step 1 写文件成功、Step 2 挂掉时，数据已落盘且没有回滚；重试再追加一遍就是双份。

**修复**：Step 1 改成按 `replace_doc_id` 覆盖写；Milvus 侧在 `add_chunks_to_index` 里先 `delete_by_chunk_ids` 再插入。

**验证**（端到端，净零改动）：

```
基线              doc570 文件 88 行 | Milvus 1525
Step2 失败后      doc570 文件 88 行   ← 不是 176
恢复后重试成功    doc570 文件 88 行   ← 仍是 88
                  Milvus 1525        ← 没涨
```

**教训**：文档里写着的原子性承诺，要**当成待验证的断言**而不是事实。这次就是被自己写的注释骗了。

### 坑 6：删除按文件名匹配，同名文档会被连带删掉

**现象**：删掉重复的两份中的一个，返回 `chunks: 130 milvus: 102`（而不是 65 / 51）——把另一份也端了。

**根因**：`_remove_chunks_of` 判据是 `c["source"] == filename`，Milvus 的 `delete_by_document(filename)` 同理。而重复文档**共用同一个文件名**。

**状态**：**已诊断，未修**。修法方向是按 doc 身份而非文件名匹配，涉及删除路径的设计变更（要不要保留同名多版本、历史版本怎么清），需要单独拍板。

### 坑 7：上传重复内容判重失效

**现象**：同一份 PDF 再传一次，返回 `accepted` 并新建了一条记录，索引里内容存了两份（分块文件 1942→2007、Milvus/BM25 1525→1576，51 个 chunk_id 各两份）。

**用户可见影响**：**BM25 稀疏路 top-8 里有 4 个名额被重复内容占掉**（同次向量路 8 条 0 重复）。最终召回列表看不出重复，因为 `_expand_to_parents` 按父块 id 去了重——重复在 RRF 融合**之前**就已经挤掉了别的文档的名额。

**根因**：判重有两层，都靠 `content_hash`，而老记录的 `content_hash` 是 **NULL**：

```python
# 上传口
WHERE content_hash = ?                                  # NULL 匹配不上 → 放行
# add_document 内部
if existing.content_hash == content_hash:               # None != "f2c1..." → False
    return existing["id"]                               # 本该走这里"跳过"
new_version = existing["version"] + 1                   # 却走了这里，插新行 v+1
```

源头是 `scripts/process_pdfs.py` 调 `add_document` 时**没传 `content_hash`**（另外两个调用点都传了）。6 份 PDF 全部中招、全部 `version=2`。

**修复**：三层
1. `process_pdfs.py` 补上 `content_hash`（现算 sha256）；
2. `add_document` 在不传 hash 时 **打 warning** —— 不再静默；
3. 新增 `db_manager.update_content_hash()` + `scripts/backfill_content_hash.py`（默认只报告，`--apply` 才写），回填了 5 条存量。

**验证**：

```
之前（hash=NULL）→ {"status":"accepted"} 新建 doc 607
现在（hash 已补）→ {"status":"skipped","message":"内容已存在，跳过入库","doc_id":570}
                   库内记录数仍是 1
```

### 坑 8：`ProgressReporter.fail()` 的 meta 格式会杀掉 Celery worker

**现象**：任务失败一次之后，worker 直接退出；更糟的是失败的消息被 restore 回队列，新 worker 捡起来再炸一次——**死循环**。

**根因**：`reporter.fail()` 把普通 dict 当作 `FAILURE` 的 result 存进去，**没有 `exc_type`**：

```
实际存的: {"progress":0, "stage":"failed", "error":"..."}          ← 畸形
正常应该: {"exc_type":"...", "exc_message":[...], "exc_module":"..."}
```

Celery 之后再解析这个 task_id 就必抛 `ValueError: Exception information must include the exception type` → `CRITICAL Unrecoverable error` → worker 退出。

**状态**：**已修**。全量日志覆盖 09-22 至今，这个报错只在 2026-10-11 首次出现——潜伏已久，被一次任务失败踩响。

**修复**：`fail()` **不再往 Celery 的结果后端写**。理由是搞清了状态语义：Celery 的 `FAILURE` 按约定必须携带异常信息（`exc_type`/`exc_message`/`exc_module`），拿它当进度通道用本身就是误用。抛异常结束的任务，Celery 自己会记一个带真实 excinfo 的 `FAILURE`，不需要我们代劳。失败照旧写 Redis + `task_logs`——那是前端状态读取的前两级（Redis → task_logs → Celery 兜底）。

想「伪造」异常信息这条路也验证过不可行：`celery.exceptions.TaskFailed` 并不存在，硬塞 `exc_type` 只会更脆。

**随之而来的取舍**（明确记录）：调完 `fail()` 后正常 `return` 的任务（如 `preview_pipeline` 的失败分支）在 Celery 侧会显示 SUCCESS，权威失败状态在 Redis/task_logs 里。彻底的做法是让这些分支 `raise`，属于任务语义变更，未做。

**验证**：真机派发两个必定失败的任务（不存在的 doc_id / 不存在的 PDF 路径），worker 全程存活（修之前 11 秒内必死），日志无新增 CRITICAL；失败状态在 Redis 里可读。单测 `tests/test_task_failure_isolated.py` 4 条，**验过有牙齿**（把 FAILURE 写入加回去 → 1 红）。

**顺带修的**：`report()` 发的自定义状态是 `PROCESSING`，而 `_CELERY_STATE_MAP` 里没有这一条 → 未知状态被 `_normalize_state` 判成 `failed`。也就是说正在跑的任务，在 Celery 兜底那一路会显示成「失败」。补了一行映射。

### 坑 9：Celery worker 里 `sys.stdout` 是 `LoggingProxy`

**现象**：任务连函数体都进不去，报 `AttributeError: 'LoggingProxy' object has no attribute 'reconfigure'`。

**根因**：`extract_triples.py` 顶部在 `win32` 下裸调 `sys.stdout.reconfigure(...)` 强制 UTF-8。普通进程里 stdout 是 `TextIOWrapper`，但在 Celery worker 里是 `LoggingProxy`，没这个方法——**import 这一步就炸**。

**修复**：提成 `force_utf8_console()` 并整段包 try（`sync_kb.py` 早就是这么写的，该抄没抄）。

**教训**：**进程内 `apply()` 验证有盲区**。当时用 `apply()` "真跑"过任务并通过了——因为它跑在普通进程里，stdout 是真对象。真 worker 11 秒就打脸。**`apply()` 不等价于端到端。**

### 坑 10：`verify()` 与「触发点」的关系

**现象**：管理台「重建知识库」按钮点完之后，图谱和盘上不一致。

**根因**：`rebuild_kb_task` 只调 `build_all()`——重写了 `kg_triples.jsonl` 却**不灌 Neo4j、不校验、不写 manifest**。而文件监听走的是 `sync_kb.main()`，两条路行为不同。

**状态**：**已诊断，未修**（改法是一行：让它调 `sync_kb.main()`，代价是同步会多跑一次回归评测）。

### 坑 11：设置页上的分块参数是假的（重构后没人接）

**现象**：`data/kb_settings.json` 里写 `max_chunk_content: 180`，页面上改也"保存成功"，但分块结果一动不动——子块上限始终是 150。测试 `test_max_chunk_content_is_a_real_parameter` 从父子分块重构后就一直红着。

**根因**：父子分块重构把细切从 `_chaptered_chunk` 挪到了 `split_parent_into_children`，参数**没跟着挪**——`max_chunk_content` 还留在 `_chaptered_chunk` 的形参表里，一路收下、一次不用（连算出来的 `content_size` 都是死赋值），子块死守常量 `CHILD_CHUNK_SIZE = 150`。同一件事有两个数字（300 与 150）就已经够说明问题了：**参数收下了不使用，比直接删掉更糟——页面上还显示它有效。**

**修复**：`split_parent_into_children` / `build_parent_child_chunks` 收下 `max_chunk_content` 当作子块上限；`_chaptered_chunk` 的三个分块形参全删（它在章节路径上一个都用不到）；`MAX_CHUNK_CONTENT = CHILD_CHUNK_SIZE` 收成一处，不再各留一个数；配置文件的 180 对齐成 150。

**验证**：按配置值 150 重切全部 417 个父块，与已入库的 1525 个子块**逐字比对** → PDF 路径 401/401 完全一致（剩下 16 个 md 父块本就是 `build_finance_kb.py` 里另一份实现产的，不归这次改动管），确认**零重切**。测试改成在子块层量长度（父块整章不设限，在原处量不出这个参数——这正是它一度从"能测出来"变成"空转"的原因）。**验过有牙齿**：拆掉接线 → 红，装回 → 绿。全量 400 passed。

## 七、经验教训（可复用到其他链路）

1. **"写好了但没接线"是最常见的 bug 形态。** 父子分块展开、`extract_triples.py`、管理台按钮——三处都是代码完整、逻辑正确，但全仓搜不到调用方。查链路完整性时，**先 grep 调用方，再读实现**。

2. **静默降级 / 静默跳过是主要风险源。** 灌库失败吞成"跳过"、判重靠一个 NULL 字段、软删计数滞后——共同点是**失败不发声**。原则：**宁可非零退出让人看见，也不要静默退化。**

3. **同一个判断写三遍，就一定会漏第四遍。** 收口到一处比复制粘贴安全，哪怕多一个函数。

4. **产物 vs 事实源的边界要写死在代码里。** 审核结果只能写源文件（写了产物会被下次构建覆盖）；校验要同口径比对（不能一边含父块一边只有子块）。

5. **文档里写着的承诺，要当成待验证的断言。** "原子性"、"幂等"、"已同步"——这次被自己写的注释骗了一次。

6. **进程会持旧代码。** 加了跨模块 import 之后必须重启 API/worker，否则报的是 `cannot import name` 这类看起来莫名其妙的错。

7. **验证测试要验证"测试有牙齿"。** 故意把修复拆掉，确认测试真的会红——否则你只是写了一个记录当前行为的快照，不是回归测试。
