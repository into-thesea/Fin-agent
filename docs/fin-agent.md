# ========== 第一部分：基础篇 ==========

## 主题一：项目定位与架构

### Q1 AI 大模型应用开发和底层原理的区别？市场需求占比？

**回答**：大模型开发分两层。底层是研究模型本身——为什么智能、用什么数学算法，要读论文、要高等数学，岗位少、要求高，大概只占 10% 市场。应用开发是把模型变成具体产品——智能客服、企业问答这类，面向商业场景，重点是把功能和工程做好、快速见效，占 90% 市场，也是大多数公司的主方向。所以对绝大多数做 AI 的人，重心都在应用层：怎么把模型接好、调好、兜住，而不是改模型本身。

**我做了什么**：我的项目就属于应用开发层——把 LLM 变成能回答理财产品问题、还能守住适当性红线和资金安全的理财客服。我做的是 LangGraph 编排、双路检索 + 图谱多跳、业务只读工具接入、确定性资金门控这些"工程活"，定位是应用层，这也是市场的主流方向。

### Q2 LLM 开发应用为什么不能仅调用外部 API？要考虑哪些因素？

**回答**：只调外部 API 只能做玩具。真实落地要考虑三块：一是**架构**——重试、兜底降级、日志、性能、跟后端业务系统的联动，一个都不能少；二是**数据安全**——企业的敏感数据不能上传外部平台，特定行业要私有化；三是**业务定制**——通用模型给不了行业能力，要整合公司自己的知识库和业务流程。

**我做了什么**：我项目里这三块都做了。架构上：主模型失败走多模型降级链、语义缓存前置、信号量限流、120s 超时，不把上游打爆；业务上：不止调 API，还接了只读理财工具（产品目录查询/适当性校验/本人持仓）和理财知识库；安全上：嵌入模型 bge 本地部署不出系统、出站 PII 掩码（手机号/身份证/银行卡号）、工具调用做归属与审计、"我的持仓/验证码/动账"这类私有问答不进共享语义缓存。

### Q6 项目技术栈架构？为什么选这些技术？

**回答**：AI 项目技术栈一般按后端、AI、前端、部署分层选型。选型的核心不是追新，而是每个组件解决什么问题、和别的组件怎么衔接。

**我做了什么**：后端 FastAPI（异步，适合高并发 LLM 应用）+ LangGraph（把多 Agent 接力/重试/确定性转人工声明式化，不用手写状态机）；AI 层 DeepSeek（`deepseek-chat`，路由/生成用）+ bge-base-zh-v1.5 本地嵌入（768 维，数据不出系统）；存储 Milvus（唯一向量后端，检索/语义缓存/用户记忆三用）+ BM25 稀疏索引 + Redis（缓存/会话/画像/审计）+ Neo4j（图谱，硬依赖）；前端 React；部署 Docker 编排中间件。关键选型逻辑：Milvus 一个向量库同时支撑检索、语义缓存、用户记忆三用；Neo4j 是硬依赖，不可用时图谱检索直接报错（不静默降级，防止两个后端图不一致导致答案依据悄悄改变）；bge 本地部署省嵌入成本又保数据安全。

### Q8 为什么需要绘制架构图？不同类型架构图的作用？

**回答**：架构图一图胜千言，解决沟通障碍。但要对人下菜：给上级/投资人看产品架构图（讲业务怎么做，别堆技术），给团队看技术架构图（识别技术需求、讲清技术关系）。

**我做了什么**：我画了三张图（docs/ 下）：业务流程图.svg、项目架构图.svg、时序图.svg，面试开场先讲业务流程图这页图再展开。架构图是分层的：表现层（React）→ API 层 → 编排层（LangGraph 状态机双后端 /chat/sync 与 /chat/stream）→ 记忆层 → 智能体层 → 工具层（含安全拦截、MCP）→ 检索层（Milvus/BM25/图谱）→ 缓存层（网关语义缓存）→ 存储层（Milvus/Redis/SQLite/Neo4j）→ 基础设施。我会对不同人讲不同层次：给技术面试官讲编排层的状态机、检索层的混合召回、资金门控节点；给业务方讲业务流程图「用户问一句 → 分流 → 查产品/检索/转人工」这条业务流。能画出并讲清这几张图，本身就说明架构是成体系的，不是散装功能拼出来的。

## 主题二：Agent 与 LangGraph

### Q10 LangChain 框架的核心功能？解决大模型开发中的哪些问题？

**回答**：LangChain 是 LLM 应用框架，解决大模型的三个硬伤：拿不到实时信息、不能执行操作、不会规划步骤。它把 LLM 跟数据源、工具、记忆串起来，让开发者不用从零造轮子。

**我做了什么**：我用的 LangGraph 正好对着三个硬伤：实时信息靠 RAG 检索理财知识库；执行操作靠 Function Calling 调只读工具（查产品/适当性/持仓）；步骤规划靠图编排让多个 Agent 接力——意图分类、申购门控、确定性转人工都是图上的节点和边。加上三层记忆注入，这就是一个完整的 LangChain 生态应用。关键是**能写死判断的业务（资金门控）不走模型，走图上确定性节点**，这点我放在讲 Agent 边界时展开。

### Q13 LangChain 中的 Chain 和 Agent 的区别及应用场景？

**回答**：本质是**流程固定还是动态**。Chain 把组件按固定顺序连成链路，写死、可控、高效，适合文档总结、固定问答这类确定任务；Agent 让模型自主决策——动态选工具、定步骤，适合多步推理、要实时信息、任务形态不确定的场景。一句记：Chain 是流程驱动，Agent 是目标驱动。工程上按任务复杂度分流，不是二选一。

**我做了什么**：我项目里两种模式是并存的、按任务分流：寒暄、简单政策问答走快速通道（规则分流 → 检索 → 生成），毫秒级返回、便宜——流程确定没必要让模型临场发挥；复杂咨询走 LangGraph 多 Agent 状态机——编排节点按 12 类理财意图派发，申购这类资金操作交给**确定性门控节点**（适当性 → 金额 → 验证码），疑似诈骗/投诉直接走确定性转人工，验收不过还能沿条件边回环重写。这个演进的判断依据是：能写死流程的任务求稳求快，需要动态拆解的任务固定管道接不住，才值得上 Agent——这正是这道题「什么场景用 Chain、什么用 Agent」的答案。

### Q38 Agent 智能体的作用？与传统 RAG 的区别？

**回答**：RAG 是"检索+生成"的单轮固定流程，适合知识问答；Agent 能动态调工具、多步推理、拆复杂任务，是"能干活"的。两者的关系不是对立——Agent 里可以内嵌 RAG。

**我做了什么**：我项目里两者结合：RAG 管知识（产品说明书/政策条款检索），Agent 管业务（查在售产品、校验适当性、查本人持仓）。例："我测评 R2 能买平衡增利 180 天吗"——RAG 先检索产品风险等级与适当性规则，Agent 再调 check_suitability 做确定性校验。单靠 RAG 只能答"政策是什么"，加 Agent 才能"查你的测评等级并判定能不能买"。

### Q49 CoT 与 ReAct 推理链的区别？适用场景？

**回答**：CoT 让模型先展示推理步骤再给答案，靠模型内部知识，适合数学、逻辑等可单步推理的任务，透明但不碰外部；ReAct 是"想→做→看"循环，模型推理 + 调工具 + 观察结果，适合要实时数据、要动态适应的任务。

**我做了什么**：简单政策问答我用 CoT 式（模型直接推理生成）；查产品/持仓这类任务用 ReAct 式（AgenticAgent 边想边调工具，最多 6 轮）。但我在实践中给 ReAct 加了约束：**申购是否放行这类涉及资金安全的判断，不用 ReAct 赌模型，改成确定性门控**（适当性等级比较、起购金额校验、验证码二次确认），这让我意识到——能写死判断的规则别交给推理链，这是 ReAct 的工程化边界。

### Q52 Agent 如何集成多种工具？工具链集成的技术要点？

**回答**：要点是工具注册与发现、模型动态决策选工具、分步推理串联多个工具。工具一多，还得管好注册、权限、结果可追溯。

**我做了什么**：工具注册表统一注册 4 个**只读**理财工具（retrieve_knowledge 检索知识库 / query_products 查产品 / check_suitability 适当性 / query_holdings 查本人持仓）；AgenticAgent 里模型输出 tool_calls → 注册表执行 → 结果回传，最多 6 轮；所有工具外面包了统一安全拦截器（越权审计）。更关键的设计是：**申购/赎回这类动账能力根本不注册为工具**——模型手里只有只读工具，放行动账在结构上不可能发生，不是靠模型自律。三个要点我全落地：注册集中、权限统一、资金安全靠"不注册"来结构保证。

### Q98 工具链集成与多 Agent 协作的系统架构设计与优化？

**回答**：多工具要支持注册、动态调用、消息路由、任务分解与合并；多 Agent 要分工协作、结果整合、容错恢复；架构上还要异步、监控、弹性。难点往往不在单点，而在状态一致性和容错。

**我做了什么**：工具注册表 + 安全拦截（越权审计）；LangGraph 状态机里 12 类意图映射到领域/门控/转人工节点，申购门控节点做确定性校验，条件边驱动验收回环；容错做了三层：审核不过回环重写、工具失败走结构化错误、模型失败走降级链；监控有 /monitor/sli + 审计日志。资金操作全程 Redis security:events 留痕，越权在金融场景按事故对待。局限我也清楚：目前单机 2-Worker + 信号量门控，扩展路径是加实例 + 负载均衡，架构不用动。

## 主题三：RAG 检索与优化

### Q27 什么是 RAG？核心流程是什么？

**回答**：RAG 一句话是"先查后答"：提问不直接进模型，先拿问题去外部知识库（向量库）按语义检索最相关的片段，再把"片段+问题"一起交给大模型生成答案。核心创新是"检索+生成"协同，治的是大模型两个通病：知识过时和幻觉。模型拿到事实材料，答案就能溯源。和传统知识库问答的区别是：RAG 让模型基于片段重新组织语言，不是把片段直接甩给用户。

**我做了什么**：我的链路比教科书多几层工程化：检索前先做**实体对齐**（问"大额存单"要落到目录全名/图谱节点，不会答成别的产品）；检索用 Milvus 向量 + BM25 两路召回 + RRF 融合 + MMR 去重，不是单路向量；对关系类/多实体问题还补一路**知识图谱多跳**，把 1~3 条带溯源的推理路径注入生成；生成后 Reviewer 反幻觉验证——答案必须落到检索材料上，否则打回重写。离线评测（105 条 Golden QA）证据覆盖率达 99.0%。

### Q28 RAG 相比传统大模型生成的优势？适用场景？

**回答**：四大优势：知识时效（能查到最新）、减幻觉（有事实支撑）、可追溯（答案带来源）、低成本（更新知识只维护库，不微调）。适用知识常变、要溯源、要私有化的场景，典型如客服、医疗、企业知识库、金融。

**我做了什么**：我的理财客服就是 RAG 的典型落地，四项优势都能对上号。可追溯：每个答案都带溯源来源（sources 字段，含图谱路径会带 🕸️ 角标），用户能点开看引用了哪篇产品说明书或政策条款；减幻觉：检索后加了 Reviewer 反幻觉验证 + 实体对齐，模型不能凭空编；低成本：知识更新只重建索引（按 '##' 章节分块 → bge 嵌入 → 写 Milvus + BM25），从不微调模型——理财产品说明书/政策经常更新，改一份文档重建索引就够了；领域适配：理财产品的收益口径、适当性规则、存款保险这些全走 RAG，模型本身不需要懂这些领域知识。

### Q29 RAG 系统的核心技术链路和关键组件？

**回答**：链路是：文档加载→分块→嵌入→向量库存储→检索→生成。每个环节都可独立优化——分块粒度影响检索粒度，嵌入模型影响召回率。

**我做了什么**：RAG 链路的每一环我都落地了，而且知道每环对结果的影响。分块：按 '##' 标题做章节分块（父块）+ 句子级二次切分（子块），父子结构——理财说明书每节一个主题，子块检索单元更聚焦；嵌入：bge-base-zh-v1.5 本地跑（768 维），单例复用避免重复加载模型；向量库：Milvus 是唯一向量后端，不可用时检索直接报错（不静默降级，防止"假混合检索"——表面双路实际只有一路）；检索：向量 + BM25 两路召回 + RRF 融合 + MMR，关系类问题再叠加图谱多跳；生成前还有 Reviewer 兜底。我最重视分块和检索融合这两环，因为实测它们对召回质量影响最大。

### Q30 在 RAG 中如何优化嵌入模型的性能？为什么要用缓存？

**回答**：嵌入计算贵、重复嵌入浪费，所以缓存：相同文本直接读缓存，命中能比重新计算快 10-100 倍。缓存目标不只是嵌入，答案也可以缓存。

**我做了什么**：我把语义缓存做到了请求最前面（gateway_cache.py）：问题→答案用嵌入向量化存进 Milvus，新问题来了先算和旧问题的余弦相似度——大于等于 0.93 说明基本是同一句话换了个说法，直接返回旧答案不跑管道；大于等于 0.82 也返回但打个标记。命中一次从跑完整管道压到 0 延迟，这是最省钱的优化。但金融场景缓存有个更严重的坑：**缓存会串用户**——「我的持仓」「验证码 123456」「我要买 5 万」这类是用户私有/动账数据，A 用户的答案绝不能因为 B 换种说法问就命中。所以我在共享缓存两侧都加了**隐私守卫**（cache/privacy.py）：用户私有 + 资金动账类问答读写都不进共享缓存，宁可漏命中多跑一次。嵌入侧同样复用：bge 模型单例加载。

### Q31 微调（Fine-Tuning）与 RAG 如何选择？

**回答**：微调是改模型权重，适合风格/格式/专业能力定型，但成本高、要准备数据、知识更新慢；RAG 是外部知识，适合知识常变、要可追溯、低维护。知识密集且常变→RAG；说话风格要固定→微调；可两者结合（检索给事实，微调管表达）。

**我做了什么**：我选了 RAG，三个实际理由：理财产品知识频繁更新，RAG 只重建索引不碰模型；答案要可溯源、要合规可审计，RAG 天然支持；不微调避开了 GPU 训练和数据准备。我还能讲升级路径：如果将来要"客服话术风格定型"或要模型学会特定产品线的表述习惯，就微调 LLM + 保留 RAG 检索。

### Q33 MMR 检索算法的原理？在 RAG 中的应用优势？

**回答**：MMR（最大边际相关性）在选结果时同时看两件事：和查询的相关性、和已选结果的差异性，用 λ 平衡。好处是去重、答案不"同质化"——不然 top-k 全来自同一段，覆盖不了多个信息面。

**我做了什么**：检索最终注入前用 MMR 重排（λ=0.5，可配置），top-k 来源更分散，回答能覆盖多个信息源，避免重复段落占名额。λ 的取舍我也能讲：调高更相关但易同质，调低更多样但可能引入不相关内容。这里还踩过一个真 bug：早期 FAISS 兜底路径取索引时用 `or` 吞掉了合法的下标 0，导致第一条向量必崩——这提醒我重排代码要小心"0 是合法值"这类边界（FAISS 兜底路径后来已删除，Milvus 改为唯一后端）。

### Q34 向量数据库的作用？主流选型对比？

**回答**：向量库存高维向量、做相似度搜索，是 RAG/推荐/图像检索的基础设施。主流对比：Milvus（分布式、大规模、元数据过滤）、FAISS（本地快、小规模）、Pinecone（云原生）、Chroma（本地原型）。量级和过滤需求决定选型。

**我做了什么**：我选 **Milvus 唯一后端**。Milvus 一个库同时支撑检索 + 语义缓存 + 用户记忆三用，可分布式、支持过滤。为什么不做 FAISS 降级：两个后端的索引可能不一致，静默换源等于悄悄改变答案依据——"看起来正常但召回质量差"的静默退化比报错更可怕。选型逻辑：企业级数据量 + 要高并发（外置向量是水平扩展前提）。踩过 Milvus 客户端/服务端版本不匹配导致加载卡死、元数据损坏的坑（pymilvus 3.x 连 2.4 服务器），重建后强制客户端对齐服务器版本。

### Q35 大模型推理和检索系统的优化手段？

**回答**：常见手段：缓存、批处理、量化/蒸馏、并发/异步、分布式部署、分层召回。核心是分清瓶颈在延迟、成本还是并发，对症下药。

**我做了什么**：检索系统的优化我按瓶颈分了几路下手。延迟：语义缓存前置，命中直接返回不碰管道；检索精度与成本：两路召回（Milvus 向量 + BM25）用 RRF 融合后再 MMR 重排，昂贵的向量只跑在必要候选上；并发：processing_slot 信号量限制同时进行的 LLM 高开销请求，避免打爆模型 API，配合 WorkerPool 线程池。模型侧也有两招：bge 嵌入本地跑不占 API、模型分层让路由/验收用便宜档。量化/蒸馏这类压模型体积的手段我留着给生产部署阶段，雏形阶段不上——因为当前的瓶颈在链路组织而不是模型推理速度，这本身就是一个判断。

### Q36 请设计一个基于 RAG 和向量数据库的智能问答系统？

**回答**：设计要点是链路完整 + 能应对知识更新：文档加载→分块→嵌入→向量库→检索（含 MMR）→生成，外加缓存监控和增量知识更新。

**我做了什么**：这道题问的其实就是我做的系统，我能把链路完整讲出来。知识入库：build_finance_kb.py 把理财产品说明书与制度文档按 '##' 章节分块（父块）+ 句子级二次切分（子块）、bge 嵌入、写进 Milvus + BM25；问答链路：LangGraph 状态机里 12 类意图分流，复杂问题走双路检索 + MMR + 图谱多跳，Agent 用函数调用去调只读工具或检索，生成后过 Reviewer 验收，最后带来源输出；缓存与监控：语义缓存前置在入口，/monitor/sli 看 QPS/成功率/缓存命中率；知识更新：传新文档重建索引、旧文档向量先删后写，文件监听自动触发同步。从文档上传到用户拿到带来源的答案，是一条能讲完整闭环的设计。

### Q40 召回率和准确率的含义及其关系？

**回答**：召回率=找全相关结果的能力，准确率=返回结果的相关性，两者此消彼长。医疗/法律重召回（别漏），广告推荐重准确（别错）。实际按业务取舍。

**我做了什么**：我的评测（scripts/eval_finance.py）对 105 条金融 Golden QA 跑离线指标：**证据覆盖**（golden 标注的知识库文档是否进了检索结果，类比"别漏"）、**路径结构一致**（多跳问题的期望路径是否真实存在于图谱）、**图谱触发率**（关系类问题是否真的触发图谱检索）。这三个指标分别对应"召回够不够、推理链对不对、图谱有没有白做"。客服场景我偏召回——宁可多捞回来让重排和模型去判断相关性，因为漏掉正确条款比多给几条候选更严重。这个取舍我会结合指标讲，比背定义有说服力。

### Q61 本地部署嵌入模型的优势、风险及典型应用场景？

**回答**：优势是数据安全（不上第三方）、可定制、长期成本低；风险是要 GPU、维护更新慢。适合政府/金融/医疗等对数据安全要求高的场景。

**我做了什么**：bge-base-zh-v1.5 本地部署：理财客户的查询、知识库数据嵌入不出系统、零嵌入 API 费、离线可用。代价是要约 400MB 内存、首次加载慢——用单例复用避免重复加载。为什么金融域尤其必要：客户问题里可能带卡号/账号，嵌入若走外部 API 等于把敏感文本送出去。高并发下讲升级路径（嵌入服务化/GPU）。

### Q63 LLM 在知识库热更新与一致性保障中的挑战与方案？

**回答**：挑战是更新时的一致性和并发：高并发下的知识同步、增量 vs 全量重建、数据冲突。方案：分布式锁、增量同步+定期全量校验、版本号/时间戳冲突合并。

**我做了什么**：更新走 build_finance_kb.py 重建索引，用"先删后写"（旧文档向量删掉再写新）保一致性。理财知识库规模小（22 篇文档 → 213 父块 + 252 子块 = 465 块），全量重建快、一致性简单。规模大了再上增量同步 + 版本号——我讲得清这个升级路径。

## 主题四：多轮对话与记忆

### Q45 大模型如何实现会话历史管理和长期记忆？

**回答**：短期记忆靠上下文窗口（会话内），长期记忆要持久化（向量库/DB）+ 跨会话检索。关键是用户级/会话级隔离，别让 A 的历史污染 B。

**我做了什么**：三层记忆（memory_store.py）：会话窗口（Redis list 最近 5 轮）解决多轮指代；用户画像（Redis hash，记录用户问过的产品/风险测评档位）做个性化；向量记忆（bge 向量化存 Milvus，**按 user_id 过滤**）做语义召回。三层在路由前融合注入，才来得及影响回答。隔离上用户级 + 会话级双隔离——金融场景这尤其重要，A 客户的持仓信息绝不能出现在 B 客户的上下文里。

### Q51 多轮对话系统如何实现会话与上下文追踪？常见方案及难点？

**回答**：方案：会话 ID + 用户 ID 隔离、持久化历史、上下文管理（滑动窗口/摘要）、动态检索相关历史。难点：历史爆炸、上下文窗口限制、数据隔离。

**我做了什么**：多轮对话的核心是「记住说过什么、还差什么」。会话状态 Redis 化，多开进程也不打架；槽位收集（slot_filler.py）负责从多句话里逐步攒产品/金额/期限/风险等级，申购缺必填槽位会追问；购买流程里"验证码 123456"这类续轮是通过识别 6 位验证码补全的。窗口不够用怎么办——滑动窗口只保留最近 5 轮原文，更早的用便宜模型压成摘要。隔离这块我踩过真坑：线程本地变量没清理导致匿名请求继承了上一个人的身份，改成每次请求统一设置/置空后才干净。历史爆炸、上下文窗口有限、数据要隔离，这三个难点我都遇到过并给了工程解法。

## 主题五：缓存与性能

### Q14 用 LangChain 开发时如何处理和优化性能问题？

**回答**：监控（延迟/成本/资源）、缓存、优化 prompt 减 token、批处理、并行、超时重试、优雅降级。别等上线再优化，每步都能测。

**我做了什么**：我在性能上做的几件事各对应一类瓶颈。第一是缓存：语义缓存前置到请求入口（gateway_cache.py），同样的问题第二次问直接命中返回，不跑 LLM 管道。第二是减 token、省成本：模型分层——路由和验收用便宜档、真正干活的领域 Agent 才用全量模型，整体省约一半 LLM 费用；检索也只喂重排后的 top-k 片段，不是把整个知识库塞进去。第三是兜底：120s 超时 + 主模型失败走降级链，不因为一次上游抖动就挂。第四是并发：WorkerPool 限 2 个重任务 + 信号量限流，防止同时打爆模型 API。监控我自建了 /monitor/sli（QPS/P50/P90/缓存命中率）——小项目自建够用，以后要上生产再换成熟监控。

### Q56 大模型行业落地的性能瓶颈有哪些？策略？

**回答**：瓶颈：推理延迟、检索慢、内存大、API 成本高、知识更新慢。对策：缓存、批处理、量化、分布式、分块检索、监控扩容。

**我做了什么**：性能瓶颈我按每一类瓶颈给的解法，而不是笼统说加缓存。延迟高：语义缓存前置在入口，同样的问题第二次直接命中返回；检索慢：向量（Milvus）+ BM25 并行召回再融合，图谱只对关系类问题做多跳、不做全量遍历；成本高：模型分层（路由/验收用便宜档省成本）+ 语义缓存减少重复调用；知识更新慢：build_finance_kb 后台重建索引，不阻塞用户在线问答；并发压力：processing_slot 信号量限制同时跑的高开销请求数，排队而不是打爆 API。向上扩展我会讲「加实例 + 负载均衡，架构不用变」——因为无状态化、向量外置、缓存前置三件事已经做完了。

## 主题六：安全与合规

### Q41/Q53 大模型应用的数据安全与合规（风险及应对）

**回答**：风险：幻觉、数据泄露、隐私侵犯、偏见、滥用。应对：事实核查、内容过滤、访问控制、加密、可追溯、数据治理。安全是落地的基础，不是加分项。

**我做了什么**：金融客服的安全比通用客服更严格，我按「能出什么问题」逐类做了防护。幻觉/编造：靠 Reviewer 反幻觉验证（正则预检数字断言 + LLM 二次审查）+ 实体对齐，模型不能把没查到的当查到；越权/隐私：查持仓/适当性这类工具执行前校验归属（当前用户身份 thread-local 绑定），不是你的持仓查不到；线程身份隔离修过一个真 bug（匿名请求继承了上一个人的身份），现在每次请求统一设置/置空；**PII 掩码**：compliance.py 在答案出站前对手机号/身份证/银行卡号强制掩码只留首尾；**收益承诺合规**：广告法绝对化用语 + 金融禁语（稳赚/零风险/承诺保本等）打星号替换；涉理财/基金/保险且谈收益却没带风险提示的答案，自动附标准风险提示（存款类不误加）；**缓存隐私**：我的持仓/验证码/动账金额问答读写都不进共享缓存，防跨用户串答；资金操作全程 Redis security:events 留痕。另外嵌入模型本地部署，敏感数据不出系统。

## 主题七：MCP 与工具链

### Q46/Q94 MCP 协议的核心原理、优势及应用？

**回答**：MCP 是模型↔工具之间的标准化通信协议：模型解析自然语言→生成工具调用指令（JSON）→通过 MCP 与服务端通信调工具→返回结果。优势：工具注册/发现、异步、跨语言跨平台，一个 MCP Server 任何客户端能用。

**我做了什么**：用 FastMCP（mcp/server.py）把只读理财工具封装成标准 MCP Server（stdio 传输，独立子进程，与主应用解耦）。任何 MCP 客户端经 JSON-RPC（initialize/tools/list/tools/call）就能调用。工具里内置了用户归属与审计，对外暴露也安全。关键前提和内部一致：**只暴露只读工具，动账不经过 MCP**。

### Q97 MCP 协议与传统 API 集成方式的对比？

**回答**：MCP 异步、有工具注册/发现、输入输出标准化，适合动态工具链、Agent 场景；传统 API 同步、接口固定，适合单一服务、强一致性。不是二选一，可以混合。

**我做了什么**：我两种都在用：内部 Function Calling 直接调只读工具（同步省一跳、低延迟）；同一批工具对外封装成 MCP（让生态客户端复用）。取舍结论：内部用 FC 求性能，对外用 MCP 求标准化。无论哪条路，动账都只在服务端确定性门控里做。

# ========== 第二部分：Agent/RAG 进阶篇 ==========

## 主题一：Agent 基础与架构

### A1 你对 Agent 了解多少呢？

**回答**：Agent 是能感知环境、自主决策、执行行动的 AI 系统，不是"一问一答"。它的本质是 LLM（大脑）+ 感知 + 记忆 + 规划 + 工具使用 + 行动：以目标为导向，自主拆任务、选工具、执行、观察结果、迭代直到完成。学术渊源是 BDI 架构，2023 起基于 LLM 的 Agent 成为主流，业界正从"能不能做"转向"怎么规模化可靠部署"。

**我做了什么**：我的理财客服就是一个落地 Agent：LLM 当大脑，LangGraph 做规划/编排，三层记忆（memory_store.py）提供记忆，只读工具 + 检索（tools/registry.py）做工具使用，Reviewer 做观察纠错。面试可以从"Agent 七要素"展开，逐一对应到我的代码——这一步很关键，因为面试官听完"Agent 是什么"多半会追问"你项目里 Agent 怎么落地的"，能逐要素对上就说明不是背概念。

### A2 Agent 和 LLM 有什么区别？

**回答**：LLM 是大脑，Agent 还需要眼睛（感知）、手脚（工具）、记忆和推理策略。类比：LLM 是 CPU，Agent 是完整操作系统——进程调度是规划、内存管理是记忆、I/O 设备是工具。只有大脑完不成实际任务。

**我做了什么**：我的 LLM 只负责"思考"（判 12 类理财意图、决定调哪个工具、生成答案），真正干活靠工具：查在售产品走 query_products、判能不能买走 check_suitability、查本人持仓走 query_holdings。单靠 LLM 答不了"我测评 R2 能不能买 R3 产品"——没有 Agent 编排和确定性校验它就是纯聊天，而且可能乱放行。用这个例子讲，比背 CPU/操作系统类比更能说明"为什么需要 Agent"。

### A3 一个完整的 Agent 智能体架构包括哪些部分？

**回答**：七个组件：角色定义（System Prompt）、规划（任务分解/CoT/ReAct）、记忆（短/长/工作）、工具集（Function Calling/MCP）、行动执行器、感知反馈、编排层（Agent Loop）。工程上还要加可观测性和安全护栏。

**我做了什么**：七件我全有、还能逐个指代码：角色→agents/prompts.py 金融客服边界块（告诉模型"你是理财产品客服、只答理财范围、不承诺收益"）；规划→LangGraph 图 + Orchestrator 按 12 类意图拆派发；记忆→三层记忆；工具→只读工具注册表 + Function Calling + MCP；行动→AgenticAgent 执行；感知反馈→工具结果回传；编排→graph/cs_graph.py（节点、条件边、checkpointer）。再加两个工程层：可观测 /monitor/sli，安全 security/interceptor.py + core/compliance.py + 资金门控节点。

### A4 Agent 的工作模式都有什么？

**回答**：主流六种：ToolsCallingAgent（单步调工具）、ReActAgent（想→做→看循环）、ReflectionAgent（自我评估修正）、PlanAndSolveAgent（先规划后执行）、Multi-Agent（多智能体协作）、Human-in-the-Loop（人机协作）。建议从简单开始，单 Agent + ReAct 能覆盖大部分场景，别过早引入多 Agent。

**我做了什么**：我的演进正好符合这个建议：先 ToolsCalling/ReAct（AgenticAgent 工具循环最多 6 轮），再加 Reflection（Reviewer 验收回环，答案不合格打回重写），再上 Multi-Agent + 确定性门控（12 类意图派发到领域/门控/转人工节点），最后 Human-in-the-Loop（疑似诈骗/投诉/适当性不匹配 → 确定性转人工坐席闭环）。演进顺序就是文档说的"从简单到复杂、需要时再加"，而且我多讲一层判断：**把资金这类高风险节点从"让 Agent 自由决定"里摘出来，换成确定性门控**。

### A5 Agent 的设计范式？了解其他范式吗？

**回答**：七大范式：ReAct（推理+行动）、Reflection（自我反思）、Tool Use（工具编排）、Planning（规划先行）、Multi-Agent Collaboration、Sequential Workflow（流水线）、Human-in-the-Loop。推理深度大致 Direct < CoT < ReAct < Plan-and-Solve < ToT。

**我做了什么**：我经历了 Sequential Workflow（固定管道）→ Multi-Agent + ReAct（LangGraph 状态机）的演进。选型依据是"任务要不要外部信息、步骤明不明确、要不要动态适应"这条判断链：简单政策问答走快速通道求快，复合咨询（买 + 具体产品 + 金额）走状态机编排 + 申购门控，疑似诈骗/投诉走确定性转人工。能讲清"为什么从流水线升级到图编排 + 为什么高风险节点反而要摘出 Agent 循环"就是这道题的加分点。

### A6 Agent Loop 听说过吗？

**回答**：Agent 的核心循环：构建上下文→LLM 推理→决策（直接回复还是调工具）→工具调度执行→结果注入→下一轮，直到任务完成或达上限。难点在退出条件和错误恢复。

**我做了什么**：我的 AgenticAgent 就是这个循环（agents/agentic_agent.py）：system prompt + 工具定义 + 消息 → LLM → 输出 tool_calls → 查注册表执行 → 结果回传，最多 6 轮。LangGraph 把循环声明式化了——退出条件（验收通过/超轮数）和重试逻辑都是图上的一条边，不用手写 while 循环。而申购/转人工这类节点干脆不在这个自由循环里——它们是图上的确定性节点。讲这个能衔接上"为什么引入 LangGraph"。

### A7 自研 Agent 项目与通用大模型助手相比，核心区别？

**回答**：通用助手是一问一答；自研 Agent 有目标导向的任务拆解、工具执行、记忆、可观测、可评测，能完成真实业务动作，不是套壳聊天。

**我做了什么**：四点区别：能干活（调只读工具查产品/适当性/持仓，资金操作走门控，不只是聊天）；能追责（答案带来源 + Reviewer 验证 + 资金审计留痕）；懂业务（12 类理财意图、槽位、适当性校验、金融合规）；可评测（105 条 Golden QA 离线评测 + 286 项单测）。把四点讲完，就证明"这不是套壳 demo"——这是面试官最想确认的。

## 主题二：Workflow vs Agent

### A8 Workflow 和 Agent 的区别？什么情况下用哪个？

**回答**：Workflow 是固定流程，确定性强、效率高，适合步骤可预测的任务；Agent 动态决策、能拆复杂任务，适合需要临场判断的。判断标准：任务路径是否确定——确定用 Workflow，不确定用 Agent。

**我做了什么**：我按意图分流：寒暄/简单政策问答走规则分流 → 检索 → 生成的快速通道（Workflow），毫秒级、便宜；复合咨询（申购/多产品对比）走 LangGraph 多 Agent 编排，且资金门控、疑似诈骗转人工这些**连"要不要 Agent 判断"都由系统定死**——流程确定的不光用 Workflow，关键业务甚至用确定性代码而非模型。这个分流本身就是"能确定流程的求效率、需动态决策的交给 Agent"的落地。

### A9 如何保证 Workflow 和 Agent 的成功率？

**回答**：失败重试、错误兜底、输出校验、确定性规则兜底、充分评测。别只靠"多调几次"，要加护栏。

**我做了什么**：确定性兜底——申购放行用确定性门控（适当性等级比较、起购金额、验证码二次确认）而不是赌模型自觉，等级不足直接拦截转人工；输出校验——Reviewer 反幻觉，不合格回环重写最多 2 次；兜底降级——模型失败走降级链、工具失败返回结构化错误让模型理解；评测闭环——105 条 Golden QA + 门控分支场景测试 + 286 项单测。四层护栏是我对"成功率"这个问题的完整回答。

### A10 上线后还有什么问题需要解决？

**回答**：诚实讲，上线后才暴露的多是工程问题：性能瓶颈、幻觉残留、知识更新、监控告警、成本控制、多用户隔离、评测闭环。

**我做了什么**：我会主动讲还在迭代的点：在线端到端评测已跑通（DeepSeek，意图准确率 88.6%、合规通过率 96.2%）；评测集已扩充到 105 条 Golden QA（含对抗样本/超纲/模糊/多实体对比）；高并发是雏形，扩展路径已设计好。Neo4j 运行时灌库已经跑通（`scripts/load_kg_to_neo4j.py` 幂等灌入，镜像源走 proxy.vvvv.ee）。主动暴露已知边界、并给出下一步怎么做，比吹嘘"全都做好了"更可信。

## 主题三：记忆与上下文管理

### A11 如何设计一个高效的 Agent 上下文维护方案？

**回答**：分层：即时上下文（当前对话，滑动窗口）、会话级（摘要，达阈值压缩）、用户级（画像/历史，向量检索）、系统级（工具定义/知识索引，相对静态）。Token 预算要分配：System 10-15% / 记忆 15-20% / 对话 40-50% / 工具结果 15-20% / 生成预留 10-15%。

**我做了什么**：我的三层记忆正好覆盖"会话级 + 用户级"：会话窗口（Redis list 最近 5 轮）、用户画像（Redis hash，记产品兴趣/测评档位）、向量记忆（Milvus 按 user_id 过滤）。注入时机在路由前（memory_store.py 的 build_memory_context）。金融场景对隔离的要求更高：画像和向量记忆都按用户隔离，绝不跨用户。Token 预算我也有配置旋钮（窗口/保留轮数/压缩阈值）。

### A12 什么样的信息放长期记忆，什么放短期记忆？

**回答**：短期放当前对话、临时指令、工具原始结果、推理中间步；长期放用户画像偏好、历史决策、项目知识、交互模式、经验教训。判断标准：时效性（几分钟就失效→短期）、通用性（只对当前任务→短期）、重要性、频率。

**我做了什么**：短期 = 当前会话轮次（Redis list，满 5 轮丢最旧）；长期 = 用户问过的产品 + 风险测评档位（Redis hash 画像）+ 历史问题向量（Milvus 语义记忆，按 user_id 隔离）。分层逻辑和标准一致：临时性信息进短期、跨会话还要用的进长期——用一个具体场景讲（上一会话问过"平衡增利 180 天"、测过 R2，这会话说"我能不能买 R3 的"，系统能接上）。

### A13 记忆压缩有哪些方法？

**回答**：LLM 摘要压缩、实体/关系提取（知识图谱）、Token 截断、渐进式摘要（L0 原文→L1→L2）、选择性遗忘（重要性评分）、向量化压缩、混合策略。推荐混合：最近 K 轮原文 + 更早摘要 + 最早实体/向量。

**我做了什么**：我用的是推荐的混合策略：最近 5 轮保留原文（滑动窗口，保证近期对话细节不丢），超过阈值后用便宜模型把更早的轮次压成摘要（保留关键结论，牺牲细节）。为什么这样？因为纯截断会丢信息、纯摘要又贵，混合是成本和保真度的折中。实体关系这条我在另一处用了——知识图谱存的是产品/政策之间的静态关系（存款保险覆盖谁、代销边界），跟会话记忆是两回事，别混淆。升级路径我也讲得清：数据量大后可上分层摘要（日→周→月逐级压缩）。

### A14 记忆压缩的触发条件？Token 阈值还是语义重要性？

**回答**：两者结合：Token 阈值决定"何时压"（窗口 70-80% 触发），语义重要性决定"压什么"。另有事件触发（会话结束/任务完成/定时）。别在关键信息还在积累时就提前压掉。

**我做了什么**：用 Token 阈值 + 轮次间隔双条件：上下文占用估算超过约 60% 且距上次压缩够一定轮次才触发——为什么加"距上次"？避免刚压完没多久又触发、来回抖动。触发后按重要性决定压哪些：关键结论保留原文，普通对话压摘要。没做逐条语义评分是因为客服场景算力预算有限，"阈值定时机 + 摘要保结论"够用，这本身就是按场景选策略。

### A15 上下文窗口不足时有哪些处理策略？

**回答**：滑动窗口、对话摘要（最常用：历史摘要 + 最近 N 轮原文）、RAG 检索历史、分层上下文管理、任务分段、上下文蒸馏（提取关键事实存结构化 JSON）。

**我做了什么**：窗口管理我三层都用上：滑动窗口只留最近 5 轮原文；超阈值用便宜模型把早期轮压成摘要，作为前缀注入（摘要 + 最近原文，正是最常用方案）；向量记忆按需召回更早相关的历史（相似的问题在 Milvus 里找）。三个策略对应的都是"窗口有限，怎么取舍"，我能解释为什么这么配而不是只报名词。

### A16 用户 Prompt 特别长、上下文溢出，除了截断还有哪些策略？

**回答**：Prompt 压缩工具（LLMLingua 等按困惑度去 token）、分段处理（Map-Reduce）、关键信息提取（先一轮 LLM 抽要点再推理）、工具卸载（长文档进向量库，prompt 只放元数据）、动态上下文选择（嵌入相似度取 Top-K 段）、结构化改写。

**我做了什么**：客服场景我主要用"工具卸载 + 动态选择"：知识库里的长产品说明书/政策文档，用户问的时候只检索相关片段进 prompt，不整篇塞；历史对话用向量记忆按需召回相关的几条，不是全量回放。长文档本身走章节分块入库，而不是靠截断硬塞——把"该放哪、不该放哪"在架构上分清楚，比单纯讨论截断策略更根本。

### A17 记忆更新时能否精准替换指定片段，还是全量重建？

**回答**：小规模可全量重建；大规模要精准更新：版本号/时间戳、分布式锁、增量同步 + 定期全量校验、冲突合并（修正→保留新、不同方面→合并、矛盾→待确认）。

**我做了什么**：知识库更新用"先删后写"：删掉旧文档的向量，再写入新分块的向量——理财知识库规模小（22 篇 → 127 章节块），全量重建快、一致性简单。画像更新是合并写入（不是覆盖，避免丢历史偏好）。图谱三元组单独管理（kg_triples.jsonl），灌 Neo4j 用幂等脚本。我会主动讲这个取舍：规模小选简单可靠的一致策略，数据量上来了再上版本号/增量同步。

### A18 存储时前后不一致如何解决？

**回答**：多版本冲突处理：新信息修正旧记忆→保留新；描述不同方面→合并；矛盾无法判断→标记待确认，加版本号/时间戳。

**我做了什么**：我在缓存层遇到一类"一致性"问题：高相似的问法可能命中到不该复用的旧答案。金融场景尤其危险——如果 A 用户问"我的持仓"被缓存在共享层，B 用户换种说法可能命中 A 的答案（串户）。解法是**缓存隐私守卫**：用户私有（我的/持仓/验证码/密码/账号/卡号）+ 资金动账（动词 + 金额/指令）类问答，读写两侧都不进共享缓存（cache/privacy.py）；通用产品规则问答仍可缓存。这个例子讲"一致性/隔离"比空谈版本号更有画面：新用户答案绝不能复用别人的私有答案，关键要素不一致就拒绝。

## 主题四：Tool / Function Calling / MCP

### A19 你了解的 Tool 调用机制是怎样的？

**回答**：三层：协议层（JSON Schema 描述工具注入上下文）、决策层（模型决定调不调/调哪个/传什么参，输出结构化 tool_call）、执行层（应用解析→调真实函数→结果回传模型继续推理）。

**我做了什么**：tools/registry.py 定义工具 Schema，AgenticAgent 循环里：模型输出 tool_calls→注册表查函数→执行→结果回传。**关键是我比标准流程多了两层**：一是统一安全拦截器（security/interceptor.py）——每个工具调用前做归属预检和审计，查持仓只查本人；二是资金动账根本不进这个循环，走图上确定性门控。讲三层机制时补一句"只读工具给 Agent、动账留确定性节点"，面试官会记住这个金融场景的工程意识。

### A20 Function Call 原理？模型如何知道该调用哪个工具？

**回答**：训练阶段：模型在 SFT/RLHF 学过大量"用户请求 + 工具描述 → 正确 tool_call"样本，学会了意图和工具描述的语义匹配。推理阶段：工具描述注入上下文，模型把用户意图和每个工具的 description/parameters 做语义匹配，匹配度高就输出 tool_call 并抽参数。工程细节：工具描述质量直接影响准确率，工具太多会混淆。

**我做了什么**：我的工具描述精简、数量少（4 个只读工具），模型选得准。这也解释了为什么我先做意图分流而不是把一堆工具全塞进去——工具一旦上百个，模型在上下文里选工具的准确率就会掉。而**最需要"调用准确率"的申购反而不用 Function Call**——它是确定性节点，从根上消除选错工具的风险。所以"控制工具数量 + 写好描述 + 关键动作不走模型"是调用准确率的前提。

### A21 如果不用多智能体方案，如何让 1000 个 Tools 正常工作？

**回答**：两阶段路由（先分类选类别，再类别内精确选）、语义检索选工具（工具向量化，只注入 Top-K）、工具分层注册（核心常驻/领域动态/长尾检索加载）、描述压缩、动态加载 + 上下文热替换。

**我做了什么**：我用的是两阶段路由思路：第一层规则/LLM 分流（规则层判简单/复杂 → LLM 层分 12 类理财意图），第二层按意图只加载相关能力——咨询类走检索 + 产品查询、适当性类走 check_suitability、持有类走 query_holdings。这样每次模型面对的候选工具很少，选得准。这就是文档说的"每次只从少量工具里选"——把 1000 个工具的问题，降级成"每次只看 3-4 个"。

### A22 MCP 和 Skill 的区别？谁占上下文窗口大？

**回答**：MCP 是工具暴露协议（Client-Server，工具 Schema 注入，执行在 Server 端）；Skill 是 Prompt 层面的能力定义（角色/行为规范/few-shot）。Skill 通常更占窗口（几百到几千 token），MCP 工具 Schema 一般 100-300 token。最佳实践：只加载当前任务需要的。

**我做了什么**：我用 FastMCP 把只读理财工具标准化暴露（MCP 侧）；系统内用"领域 Agent + prompt"组合（Skill 思想）。两者我都在用，正好说明关系：Skill 教 Agent"怎么答理财产品问题、怎么守合规边界"（行为），MCP 给 Agent"查产品/适当性/持仓的工具"（能力）——一个管怎么想，一个管能做什么。

### A23 如何让大模型格式化输出？Pydantic 相比 Prompt Engineering 的优势？

**回答**：三种方案：Prompt 让模型输出 JSON（可能不遵守、要手动解析校验）、Structured Output/JSON Mode（模型层保证 Schema，但非所有模型支持）、Pydantic + 后处理（Schema 自动转 JSON Schema 注入，输出自动校验——推荐工程方案）。

**我做了什么**：意图路由我用结构化 JSON 输出：固定枚举（12 类理财意图），全局锁格式、只换枚举值和提示词，换模型不破坏解析层。为什么不用裸 prompt 让模型答？因为结构化输出能自动校验、解析稳定、还能写测试——工程上可维护性完全不一样。路由模型异常时还有关键词/正则规则兜底（按资金安全敏感度排序，诈骗关键词优先），这个对比我能讲出取舍。

### A24 MCP 特别多的话怎么管理？

**回答**：MCP 网关/Registry（服务发现、负载均衡、健康检查、访问控制）、按场景分组（每会话只激活相关组）、动态激活/去激活、权限分级（OAuth scope）、监控告警。

**我做了什么**：我的 MCP 规模小（4 个只读工具），但我能讲清升级路径：如果接入几十个 MCP Server，就用网关集中管理 + 按业务分组（产品咨询组/持有服务组）+ 动态加载，避免把所有工具描述一次性塞进上下文。面试点在于"从小规模讲清扩展思路"——我不吹做过大规模，但能说明白真遇到大规模该怎么设计。

## 主题五：Multi-Agent 与编排

### A25 你是怎么做意图识别的？怎么提升准确率？

**回答**：意图识别是 Agent 第一道门。规则/关键词快但浅，LLM 分类准但贵，两者结合最稳。提升准确率：两层路由、覆盖边界 case（未知意图）、持续评测迭代。

**我做了什么**：两层分流：规则层（query_router.py，正则 + 关键词毫秒级判寒暄/简单事实/复杂）→ LLM 层（router_agent.py，few-shot 输出 JSON 意图 + 实体，12 类理财意图）。未知意图直接走 unknown 处理不给幻觉机会；LLM 路由异常走关键词/正则规则兜底，顺序按资金安全敏感度排序（诈骗/投诉优先）。评测配套有专门测试 + golden 回归。

### A26 主流 MultiAgent 框架？状态同步难点在哪？

**回答**：主流：LangGraph、CrewAI、AutoGen、MetaGPT。状态同步难点：共享状态一致性、任务分配、结果整合、容错恢复、消息一致性。

**我做了什么**：用 LangGraph（图 + 状态 + checkpointer）。状态同步我踩过两个坑并解决：一是线程级用户身份泄漏（business/context.py，任务线程串了 → 每次请求统一设置/置空 + 图节点绑定 user_id）；二是申购这种跨轮次流程（先给产品金额、再补验证码）的状态承接，靠 checkpointer 会话快照 + 槽位聚合。这两个都是"状态在多个执行单元之间怎么隔离、怎么传"的真实问题——讲出踩坑比讲框架特性更有说服力。

### A27 多 Agent 怎么实现？之间如何通信协作？

**回答**：消息传递（结构化消息，不共享原始上下文）、Orchestrator 统一调度、任务分解→各 Agent 执行→结果合并、容错（子 Agent 失败重试/降级）。

**我做了什么**：LangGraph 里：Orchestrator 按意图把请求派到领域节点（finance_node 做知识问答、subscribe_node 做申购门控、handoff_node 做确定性转人工）→ 节点间通过图状态传结构化结果（槽位、门控判定、来源）→ 条件边驱动回环/接力。节点之间传的是产品/金额/验证码/判定结果这些结构化字段，不是整个对话历史。**节点传结构化结果而非原始上下文，就是防上下文污染的工程手段**——我这样讲，把"多 Agent 通信"从概念落到具体实现。

## 主题六：反思 / 规划 / 异常与熔断

### A28 你的 Agent 是怎么实现 ReAct 模式的？

**回答**：Thought→Action→Observation 循环：模型先推理，输出工具调用，观察结果后继续，直到完成。灵活但不可控，关键业务要加护栏。

**我做了什么**：AgenticAgent 工具循环（agents/agentic_agent.py）：模型输出 tool_call→执行→结果作为 observation 回传→再决定下一步，最多 6 轮。**但申购放行这类资金判断不靠 ReAct 自觉，走确定性门控**——这是我理解 ReAct 边界后加的护栏：能写死判断的规则（适当性等级比较、起购金额、验证码）别交给推理链赌模型自觉，这也是金融场景 ReAct 工程化的关键一步。

### A29 什么是 Agent 的反思机制？

**回答**：Reflection：Agent 输出后切换到"批评者"模式，检查准确性/完整性/逻辑，发现问题自动修正重生成。典型实现 Reflexion。

**我做了什么**：ReviewerAgent（agents/reviewer_agent.py）：先本地预检（正则查回答里的数字断言是否在检索上下文、引用来源是不是检索来源子集、检索有货却答"未找到"、长回答没带来源）→ 需要时再 LLM 审查，reject 最多重试 2 次并注入反馈修正。关键设计是**分层反思**：先廉价规则、再昂贵 LLM，控制成本——很多简单答案不用花第二次模型调用的钱，这是"反思机制"能落地的前提。确定性转人工/门控这类节点直接跳过 LLM 审核（静态话术 + 系统判定，无需反幻觉）。

### A30 Planning & Solve vs ReAct vs Reflection 的区别？

**回答**：Plan-and-Solve 先全局规划再执行，全局视野好但灵活性差；ReAct 边想边做，灵活但可能局部循环；Reflection 加自我评估层，准确高但多一次调用。推荐混合：全局规划 + 子任务内 ReAct。

**我做了什么**：我按任务选：简单政策问答走快速通道；复合咨询（申购/对比）走 Orchestrator 先判意图再派发、子步骤用工具循环；答案质量靠 Reviewer 反思兜底。**高风险的资金动作既不用 ReAct 也不用 Reflection——用确定性门控**。这正是比"混合模式"更进一步的取舍：不是所有决策都该交给模型，有些决策该由系统代码做。我能把选型理由讲清楚。

### A31 任务分解后，会根据执行结果调整任务列表吗？

**回答**：会。子任务失败或产出不符预期时重新规划、跳过、补任务，对应 ReAct 的"观察后修正"。

**我做了什么**：LangGraph 条件边天然支持：申购门控里"适当性不足"→ 走拦截转人工分支（不继续走申购）；"验证码错误"→ 停在门控节点让用户重发，不往下走；审核不通过→ 沿边回环重写。**条件边让"根据结果改流程"是声明式配置，不是手写 if-else**——这是图编排相比硬编码管道的优势，我拿申购门控这个真实例子讲，比抽象说"会调整"更有画面。

### A32 如何处理异常情况？Agent 会不会纠正自己的行为？

**回答**：工具失败返回结构化错误让模型理解、超时重试、回滚（撤销副作用）、熔断（降级/终止）、错误信息注入下一轮推理。

**我做了什么**：四层异常处理：工具失败→返回结构化错误（不抛异常），模型能看懂并换方案；超时→120s 超时 + 主模型失败走降级链（多模型）；纠错→Reviewer 拒绝后回环重写 + 注入上次的反馈；熔断→信号量限流防止打爆。金融场景还有一层：**资金操作失败绝不留半笔账**——申购校验不通过就不写持仓，通过才写并留痕，没有"部分成功"的中间态。**异常处理 + 资金操作原子性是 Agent 工程化和 demo 的分水岭**，面试讲这个能立刻和其他"只调 API 的 demo"区分开。

### A33 对 Agent 有没有熔断机制？基模卡死后端有什么保底？

**回答**：限流、超时熔断、降级到备选模型/兜底答案、异步防阻塞。基模不可用时的保底：降级链、缓存兜底、人工通道。

**我做了什么**：限流（processing_slot，BoundedSemaphore 同一时间限制高开销任务）；超时 120s；降级（主模型按序降备选模型、Milvus/Neo4j 是硬依赖——不可用时直接报错，不静默降级，防止"看起来正常但答案依据悄悄改变"）；保底（语义缓存命中直接返回不碰模型）。**金融客服场景的终极保底是转人工**——模型挂了、超时或遇到疑似诈骗/投诉，就把用户转给坐席，工单 open→take→reply→close 全程留痕，这是业务层的兜底通道，也是人机协同的意义。能把"熔断"讲到"业务兜底"这一层，说明想清楚了。

## 主题七：安全与幻觉

### A34 Agent 存在什么安全问题？

**回答**：六大威胁：Prompt 注入（直接/间接/分段/编码绕过）、工具滥用、数据泄露、模型窃取/投毒、幻觉风险（Agent 里幻觉=错误行动）、权限提升（组合低权限工具达成高权限操作）。

**我做了什么**：工具滥用/权限提升→统一安全拦截器（security/interceptor.py：工具归属预检、越权写审计）+ 只读工具集（动账不在工具里，权限提升无从谈起）；数据泄露→归属校验 + 线程身份隔离（修了匿名请求继承身份的 bug）+ 出站 PII 掩码 + 用户私有问答不进共享缓存；幻觉=错误行动→确定性门控（申购放行是代码判定不是模型）；Prompt 注入→金融客服边界块约束 + 工具层二次校验，诚实讲未做完整注入防御（可作为可补强点说出来）。六大威胁我至少对上了四类防护，能逐条对上就说明是真做过安全。

### A35 安全护栏如何实现敏感词拦截？

**回答**：三层：关键词匹配（毫秒级）、正则模式、AI 分类器（语义级）；输入输出都过；维护：词库定期更新、误杀反馈。

**我做了什么**：compliance.py 做了**金融域专属**的出站合规，比通用敏感词多两类。一是 PII 掩码：手机号/身份证/银行卡号正则识别后强制掩码只留首尾，不出现在任何对外回答；二是金融禁语：广告法绝对化用语（绝对/最好/顶级…）+ 收益承诺类禁语（稳赚/零风险/承诺保本/保证年化…）打星号替换；三是对涉理财/基金/保险且提到收益/基准/年化但没带风险提示的回答，自动附标准风险提示"理财/基金/保险非存款、产品有风险、业绩比较基准不构成收益承诺"（存款类不误加）。这三条都是规则级、可单测。比通用方案少了"AI 分类器"层——因为词表 + 正则够用，加模型分类器反而增加延迟和误杀。**按场景选拦截深度，不盲目堆模型**，这是我的取舍依据。

### A36 如何维护 Agent 生成的证据链，怎么确保不出现幻觉？

**回答**：证据链：记录每个事实声称的来源/置信度。减少幻觉：RAG 增强、强制引用来源、事后验证（另一 LLM 校验）、置信度标注、人工审核高风险输出。

**我做了什么**：证据链→答案带溯源（sources 字段，图谱路径会带 🕸️ 角标，能点开看引用哪篇产品说明书/哪条推理路径）；强制引用→Reviewer 检查引用是否在检索材料里、是否引用未提供的来源；事后验证→Reviewer LLM 二次审查（检索有货却答"未找到"会打回）；确定性兜底→申购/适当性这类业务判断不走模型。**Reviewer 双层（正则预检 + LLM 审查）是"低成本 + 高覆盖"的组合**，这是我能控制幻觉率又控制成本的关键。

### A37 Agent 如何减少幻觉？工业场景怎么做？

**回答**：RAG 最核心（回答基于真实文档）、Grounding 接地（输出与真实数据源验证）、Self-Consistency（多次采样）、输出后处理（事实检查/数值校验）、Prompt 约束（"不确定就说不知道"）、模型选择（低幻觉率模型）。

**我做了什么**：RAG→检索必带来源 + Reviewer 校验 grounded；Grounding→申购/收益这些关键判断走确定性工具/门控，不让模型编；实体对齐→tools/registry.py 检查查询点名的产品有没有真的在检索内容里，不在就明确"不应采用无关内容"（问 A 产品不答成 B）；Prompt→金融客服边界块明确"只基于提供的材料回答，不承诺收益"。**检索质量直接决定幻觉率，所以我把评测做成了闭环（golden 证据覆盖）**——从源头压幻觉，而不只是靠事后拦截。

### A38 大模型应用中常见的幻觉有哪些类型？

**回答**：三类：事实幻觉（编造/张冠李戴）、推理幻觉（逻辑跳跃/计算错）、忠实度幻觉（与上下文不一致/总结加料）。缓解：RAG + 事实校验 / 代码执行验证 / NLI 一致性。

**我做了什么**：我的 Reviewer 主要拦两类：忠实度幻觉（检索有货却答"未找到"、引用未提供来源）和事实幻觉（数字断言不在检索上下文）。推理幻觉靠确定性门控兜底（适当性/申购判定不靠模型算）。金融域还多拦一类"承诺幻觉"——模型承诺保本/稳赚，靠合规层禁语替换兜住。**不同幻觉类型对应不同拦截手段**——能说清"我拦的是哪类、用什么手段拦"，说明不是背了一个"反幻觉"名词。

## 主题八：评测

### A39 Agent 如何评估？有什么指标，数据集哪里来？

**回答**：功能指标（任务完成率、输出质量 LLM-as-Judge、工具调用准确率、意图准确率）、效率（推理步数、端到端延迟 P50/P95/P99、Token/API 消耗）、可靠性（异常率、死循环率、幻觉率）、体验（满意度、重新生成率）。数据集：公开基准（GAIA/SWE-Bench）+ 业务日志 + 专家构造 + 对抗样本 + 用户反馈。

**我做了什么**：我搭了分层评测：离线层（scripts/eval_finance.py，无需 LLM）跑 105 条 Golden QA，出证据覆盖 / 路径结构一致 / 图谱触发率（golden 里含 expected_path，专门验证多跳推理链）；在线层（--with-answers，需 DeepSeek）出意图准确率 88.6% / 合规通过率 96.2%（合规哨兵用例：risk_required 的答案必须带风险提示）。数据集构造：理财产品说明书/政策 → LLM 生成 QA + 人工校验，覆盖简单事实、多跳（带期望路径）、合规哨兵三类。**评测体系是"改进可证明"的前提**——先修评测，再谈优化，每一步改进都有数据归因。

### A40 真实智能体上线前如何构造数据集进行准确性测试？

**回答**：真实数据采集（历史日志脱敏）、专家构造（正常+边界+异常）、LLM 辅助生成、对抗样本（模糊/错别字/注入/超长）。管理：版本化、按场景分层、定期更新。

**我做了什么**：构造 105 条 Golden QA 时按场景分层：简单事实（这款产品什么风险等级/是存款吗）、多跳（银行理财是存款吗、存款保险赔吗 → 带 expected_path）、合规哨兵（答案必须带风险提示/不能承诺保本）、对抗样本（超纲/模糊/多实体对比）。数据集版本化——每轮代码或 prompt 改造后回归，防止改一处坏一处。构造数据集不是随手写几条，而是"正常 + 边界 + 合规 + 对抗"都要覆盖，我能讲出分层逻辑。

### A41 商业化评测怎么做得更好？

**回答**：多维度矩阵（功能/可靠/效率/安全/体验）、分层评测（L1 单元→L2 集成→L3 场景→L4 A/B→L5 验收）、自动化流水线（CI 触发 + LLM-as-Judge + 通过率门禁）、综合打分（Agent Score = 加权完成率/质量/效率/安全 - 成本）。

**我做了什么**：我的评测做到 L1-L3 雏形：单测（286 项，覆盖门控各分支/合规/PII/图谱/缓存守卫）→ 路由与接口测试 → 离线场景评测（105 Golden QA）。升级路径：在线 LLM-as-Judge 答案质量（已有 --with-answers 入口，已出在线指标意图 88.6%/合规 96.2%）+ 上线后 A/B 对比。**从雏形讲清商业化五层级，我到 L3，再往上是 A/B**——知道自己做到哪一步、缺什么，比吹"我有完整评测"诚实得多。

## 主题九：Prompt 与模型选型

### A42 如何写好 Prompt？Prompt 设计的规则？

**回答**：角色定义清晰、任务目标明确、输入输出格式约束（结构化）、边界约束写明（"只基于提供的材料回答，不确定就说不知道"）、few-shot 示例、防御性指令（防注入）。

**我做了什么**：agents/prompts.py 金融客服边界块：角色（理财产品客服）、范围（12 类意图 + 只答理财域）、行为约束（不承诺收益、不承诺保本、只基于提供的材料回答）、结构化输出（意图枚举 JSON + 实体）。**Prompt 是 Agent 的"软件"**——我的边界块同时约束了行为和输出格式，还跟合规层配合（prompt 说不准，compliance 层再强制），写一个能框住模型的 prompt + 一层兜底代码，比写一堆花哨指令更重要。

### A43 如何优化 Prompt Engineering 以减少 Token 消耗？

**回答**：精简 prompt 去冗余、结构化输出而非长描述、动态按需注入（只加载当前任务需要）、控制 few-shot 数量、模型分层（简单任务用便宜模型）。

**我做了什么**：模型分层（路由/验收用便宜档，省成本）；按需检索（只注入重排后 top-k + 图谱只对关系类问题注入，不是整个知识库）；记忆按需（向量记忆只召回相关历史）；结构化输出（意图固定枚举，不啰嗦）。四招背后是同一个思路：**能不放的就不放，该放多少算好预算**——token 不是越多越好，是把预算花在关键上下文上。

### A44 模型选型有什么考虑？（不同任务用不同模型）

**回答**：按任务复杂度/延迟要求/成本/幻觉敏感度分层；推理模型 vs 指令模型；国内可用性。别一个模型打天下。

**我做了什么**：分层（路由/验收用便宜档、领域 Agent 用主模型）；嵌入（bge 本地部署，省 API 费、数据不出系统）；降级链（主模型失败降备选）。金融域选型还多一层考量：**合规与幻觉敏感度**——涉及适当性/申购的环节不依赖特定模型的"自觉"，用确定性代码 + 规则兜底，所以模型选型更多影响表达质量、不影响资金安全。选型的逻辑是**按"这个环节需不需要深度推理、是不是资金关键路径"来分层花钱**。

### A45 微调 / 换更大模型 / 上下文工程 / 提示词工程，哪个性价比最高？

**回答**：性价比排序一般：提示词工程 > 上下文工程（RAG）> 换更大模型 > 微调。先试最便宜的，效果不足再升级；微调是最后手段（数据贵、周期长、更新慢）。

**我做了什么**：完全符合这个排序：RAG（上下文工程）解决知识问题 + 提示词工程（边界块/结构化输出）解决行为问题 + 模型分层控成本——全程没微调。**为什么我的场景不微调：理财知识频繁更新，RAG 只重建索引**；如果将来要固定客服话术风格，才考虑微调。我按"先便宜后贵"的决策链走，每一步都能说清为什么没上更贵的手段。

# ========== 第三部分：金融域专项（知识图谱 / 资金门控 / 合规 / 评测） ==========

> 说明：以下题目一部分由源题库行业题（AI+金融风控 / AI+政务数据安全 / 知识图谱）延伸而来，另一部分从项目本身的高频追问提炼，面试前重点准备。

## 主题一：知识图谱与多跳推理

### F1 知识图谱和向量检索有什么区别？什么场景需要图谱？

**回答**：向量检索解决"语义像不像"——把文本embedding后按相似度召回，适合"问一段话找相关文档"；知识图谱存的是**实体之间的结构化关系**（头—关系—尾），能回答"实体 A 通过什么路径和实体 B 相连、中间隔了几跳"这类**关系推理**问题。RAG 是"找资料"，图谱是"推关系"。代价：建图谱要人工/抽取维护、只覆盖定义好的实体关系，规模做不大；向量检索全自动但要靠相似度猜。所以图谱适合**关系固定、推理要可审计**的领域，金融/医疗/政务是典型。

**我做了什么**：我的理财客服在双路文本检索之外加了**第三路图谱多跳**。从 24 款产品说明书与政策文档抽了 180 条三元组（存款保险覆盖/不保、代销边界、保险犹豫期、适当性、征信影响链），每条三元组挂回原文文档做溯源。检索时先做**实体解析**（口语"大额存单"能映射到目录全名和概念节点"存款"），命中关系类或多实体问题就沿图做**双实体有向路径查询（≤3 跳）+ 邻居补全**，把"头—关系—尾（依据文档）"的路径句子注入生成。比如"银行理财是存款吗？存款保险赔吗"这类，靠向量像不像答不准，图谱能把"理财产品→不是→存款→受存款保险保障"这条链推出来。结果：离线评测多跳问题的期望路径与图谱实际结构一致率 83.3%。前端溯源证据里图谱来源用 🕸️ 角标标出"含推理路径"。

### F2 图谱证据会不会注入得太泛、变成噪音？怎么控制？

**回答**：图谱检索的典型问题：一是**过度注入**——把不相关的三元组也塞进 prompt，稀释关键信息还烧 token；二是**枢纽节点爆炸**——"理财/存款/基金/保险"这类概念出边多且泛化，一展开全是常识子类。控制手段一般是：限定注入范围（只对关系类/多实体问题注入）、过滤枢纽节点、控制注入条数、保留溯源。

**我做了什么**：做了三层门控。一是**意图门**：只在命中关系类语义（是存款吗/保不保/影响/区别/和…/犹豫期）或解析出 ≥2 个实体时才注入图谱证据，产品罗列类、单实体咨询不注入——golden 评测里"罗列类问题不注入图谱"是显式断言；二是**节点门**：把理财/存款/公募基金/保险产品这几个**概念枢纽**排除在单实体邻居展开之外，避免泛化子类噪音；三是**数量门**：双实体路径找到后优先用路径证据，邻居补全只补没进路径的剩余实体，注入上限 3 条、检索条目上限 8 条。评测里关系类问题稳定注入 1~3 条带溯源的图谱证据，罗列类不注入——"该注入才注入"是我对图谱噪音控制的核心回答。

### F3 图谱后端挂了怎么办？怎么保证链路不断？

**回答**：图谱不是检索的必需品，是增强。工程上有两种思路：一是**硬依赖 + 快速失败**——图谱不可用时直接报错，不静默降级，防止"看起来正常但答案依据悄悄改变"（两个后端的图可能不一致，静默换源等于悄悄改变答案依据）；二是**降级跳过**——图谱故障时只走文本检索，链路不断但少了关系推理能力。选哪种取决于业务对图谱的依赖程度和对"静默退化"的容忍度。

**我做了什么**：Neo4j 是**硬依赖**——不可用时图谱检索直接报错（不静默降级到内存邻接图）。原因是早期做过内存邻接降级，但发现两个问题：一是内存图和 Neo4j 的数据可能不一致（灌库脚本只灌 Neo4j，内存图从 jsonl 载入，两边数据不同步）；二是"Neo4j 起不来也能用内存兜底"的降级设计掩盖了真实后端的 bug（D9 就是典型——内存降级掩盖了 Neo4j Cypher 语法错误，上线才炸）。所以后来删除了内存降级，Neo4j 改为硬依赖。灌库用幂等脚本（`scripts/load_kg_to_neo4j.py`），图谱条目的 source 字段标成"知识图谱-<依据文档>"，和文本检索条目同构，下游统一处理。这个"硬依赖 + 快速失败"的设计本身就是答案的一半：宁可报错让运维发现，也不要静默退化让用户拿到质量差的答案。

## 主题二：确定性资金门控（不赌 LLM 自觉）

### F4 为什么资金动账不能交给 Agent 自由调用工具？怎么设计的？

**回答**：LLM 是概率系统，再好的模型也会偶发"不守纪律"——该拒绝的放行、参数抽错、被 prompt 引导越权。资金动账一旦放错就是真金白银的损失和监管问题，**不能靠"模型自觉"兜底**。设计原则：能写死判断的规则用确定性代码；动账类能力不给模型"自由开关"；高风险路径加二次确认 + 人工兜底 + 全程留痕。

**我做了什么**：两个层面。一是**结构上不让模型碰动账**：申购/赎回/撤单根本不注册成 Agent 工具，模型手里只有 4 个只读工具（检索/查产品/适当性/查本人持仓）——放行在结构上不可能，不是靠提示词劝它别乱来。二是**申购走确定性门控节点**（subscribe_node）：归属校验 → **适当性判定**（客户测评等级 < 产品风险等级 → 拦截转人工，如 R2 客户买 R3 产品）→ 起购金额校验 → **短信验证码二次确认** → 全部通过才写持仓 + Redis 审计留痕。每个分支都有明确话术和单测。结果：R2 客户申购 R3 产品被确定性拦截并转人工双录，金额不足/验证码错误/重复持有各自给出明确提示，离线门控场景测试全过。

### F5 适当性（风险等级匹配）为什么不用模型判断？

**回答**：适当性是监管红线（《商业银行理财业务监督管理办法》要求产品风险等级与客户测评等级匹配），而且它是**可以用规则确定性判断**的：客户测评档位 R1~R5、产品风险档位 R1~R5，比较两个等级就行。确定性判断能保证 100% 不误放行；模型判断是概率的，偶发就会把 R2 客户放去买 R3 产品，一次放错就是合规事故。**凡是能写成规则的合规判断，都应该用代码而不是模型**。

**我做了什么**：check_suitability 就是纯规则实现：从 mock 客户资料拿 investor_level，和产品目录的 risk 字段做等级比较（等级映射表），不匹配返回拦截话术 + handoff 标记。申购门控节点里同样先做这一道确定性判定。工具层和门控层都接了 Redis security:events 审计，"越权在金融场景按事故对待"。这套"确定性规则能判断就不赌模型自觉"的思路，是我在面试里作为金融场景工程化核心亮点讲的。

### F6 申购要二次确认吗？怎么防止用户误操作或被骗操作？

**回答**：资金操作必须二次确认，常规做法是短信/验证码验证，确认"是本人、知悉风险、坚持操作"。风险点：一是误操作（点错金额/产品）；二是被诱导操作（诈骗分子让受害者转账）。所以金融客服对"疑似被骗/飞单/内部高收益渠道"这类信号要**确定性转人工**，不能继续顺着话术引导操作。

**我做了什么**：申购门控要求**短信验证码二次确认**（演示账号 u001/u002/u003 各配验证码），验证码不对就停在门控节点让用户重发，不写持仓；演示持仓里同一产品未到期会提示"避免重复申购"。同时**疑似诈骗/飞单/投诉走确定性 handoff_node**（fraud_report/complaint 意图直接映射转人工，静态话术 + handoff 标记，不做 LLM 幻觉审核也不引导操作），例如"朋友推荐的内部高收益理财靠谱吗"会命中诈骗信号转人工。转人工升级为工单闭环（open→take→reply→close + 坐席工作台），全程留痕可追溯。**二次确认 + 疑似诈骗转人工**就是我对这道题的完整回答。

## 主题三：金融合规（PII / 收益禁语 / 风险提示 / 缓存隐私）

### F7 金融客服的合规和通用客服有什么区别？做了哪些？

**回答**：通用客服的合规主要是内容安全和隐私；金融客服多三层：一是**PII 强度**（卡号/身份证/手机号不仅不能泄露，最好掩码后都不出现）；二是**不当收益承诺**（"稳赚/零风险/保本高收益"是金融禁语，AI 不能顺着说）；三是**风险揭示**（涉理财/基金/保险的收益表述必须带风险提示，监管要求）。再加上缓存层不能把"我的持仓/验证码"这种用户私有问答串给另一个用户。

**我做了什么**：做了出站合规层 compliance.py：PII 正则掩码（手机/身份证/银行卡只留首尾）；广告法绝对化用语 + 金融禁语打星号替换；对涉理财/基金/保险且提到收益/基准/年化但原文没带风险字样的回答，自动附标准风险提示"理财/基金/保险非存款、产品有风险、业绩比较基准不构成收益承诺"——**存款类（大额存单/结构性存款）不误加**，因为存款有存款保险，加"非存款"反而错误。缓存侧做了隐私守卫：我的持仓/验证码/动账金额这类读写都不进共享缓存。这三层都配了单测（test_compliance_finance / test_cache_privacy）。金融域最怕两类事故——泄露隐私和承诺收益，我把它们做成代码级强制，而不是靠 prompt 提示词约束。

### F8 缓存为什么会串用户？金融场景怎么防？

**回答**：语义缓存通常是"问题→答案"的全局共享缓存，按问题的相似度命中。**通用问题可以复用**（"怎么买理财"换十种问法答案一样）；但**用户私有问题不能共享**——A 用户问"我的持仓有哪些"，如果缓存了答案，B 用户问"我的持仓"或换种说法，相似度一高就可能命中 A 的答案，这就是串户/隐私泄露。防法：私有和动账类问答不进共享缓存，读写两侧都拦。

**我做了什么**：专门写了一层缓存隐私守卫（cache/privacy.py），在语义缓存的读写两侧都做判定：命中用户私有信号（我的/持仓/挂失/验证码/密码/账号/卡号/余额）、6 位验证码、或"资金动账动词（买/申购/赎回/撤单）+ 金额/指令化表述"的问题，直接跳过共享缓存走完整管道。通用产品规则问答（怎么买/能随时赎回吗）不含用户信号，仍可缓存省钱。这套守卫在离线评测和单测里覆盖。金融场景我宁愿多跑一次管道，也不能让另一个用户换种说法命中别人的持仓答案——**宁可漏命中，不可错命中**。

## 主题四：金融评测与在线指标

### F9 怎么评测一个金融问答 Agent 而不是只看"答得像不像"？

**回答**：评测要按能力分层，不能只看生成文本像不像。金融场景至少看：**检索层**（该引用的文档有没有被召回到——证据覆盖/Recall）、**推理层**（多跳问题的推理路径对不对——期望路径是否在图谱里）、**合规层**（涉收益答案是否带风险提示、有没有承诺保本——合规通过率）、**意图层**（是否判对了 12 类意图）。golden 数据集按这些维度构造，再拆离线（不需要 LLM）和在线（需要 LLM）两档。

**我做了什么**：scripts/eval_finance.py + data/eval/finance_qa_golden.jsonl（105 条）。golden 分四类：简单事实（带证据文档标注）、**多跳**（带 expected_path 期望三元组路径，专测图谱推理）、**合规哨兵**（risk_required，答案必须带风险提示）、**对抗样本**（超纲/模糊/多实体对比）。离线指标：证据覆盖（golden 标注的 KB 文档是否出现在检索 local sources）、路径结构一致（期望路径三元组是否真实存在于图谱，与图谱自洽）、图谱触发率（多跳问题是否真触发图谱检索并返回路径证据）——离线无需 LLM 就能跑。在线指标（--with-answers，需 DeepSeek）：意图准确率 88.6%、合规通过率 96.2%。离线评测把"答得好不好"拆成可归因的维度，这比"看着像"可靠得多。

### F10 在线评测需要 LLM，怎么跑？跑不通怎么办？

**回答**：在线评测依赖真实 LLM（判断意图、判断合规），需要配好 key、网络可达。没配好时**离线指标仍然能跑**——证据覆盖、路径一致、图谱触发这些不需要 LLM，能先证明检索和推理是对的。这是评测设计上的降级：离线保底、在线补全。成本和额度也要控——评测集要能限条数跑。

**我做了什么**：eval_finance.py 的离线部分不依赖 LLM（证据覆盖/路径/图谱触发从检索结果和图谱直接算），所以我先跑通了离线：证据覆盖 99.0%、路径一致 83.3%、图谱触发 45.7%（这些数字来自 105 条 Golden QA 的离线输出）。在线部分（意图准确率/合规通过率）需要 DeepSeek，我把它做成 --with-answers --limit N 的可限量入口，配好 .venv 的 deepseek-sdk + LLM_PROVIDER=deepseek + 网络直连就能出。在线指标已出：意图准确率 88.6%、合规通过率 96.2%。评测要能拆出"不看 LLM 也能验证"的部分，这是工程化评测的关键——离线先行证明检索和推理对，在线补全证明端到端质量。

# ========== 第四部分：开发—测试—上线 踩坑复盘 ==========

> 面试官问"你项目里踩过什么坑/最难的问题是什么"时,不要报流水账,要挑**有代表性、能讲清现象→根因→修复、且体现工程判断**的问题讲。下面是这个项目从开发、测试到上线真实遇到并修掉的重要问题,按阶段分组。每条都能当成一个完整的小故事讲。
> 库版本不兼容、换 API 端点这类琐碎问题不提(除非它暴露了更深的设计问题)。

## 一、开发期：并发与状态一致性

### D1 多请求并发卡死：大模型同步调用把事件循环堵死了

**现象**：压测/实测多个请求同时进来时,服务整体卡住,后来的请求全部排队等死,像是死锁。

**根因**：最初聊天链路里直接用同步方式调大模型 SDK,而 FastAPI 跑在异步事件循环上。一个请求发起 LLM 调用时把事件循环阻塞住,其他所有请求都干等——单请求串行没问题,一旦并发就暴露。更隐蔽的是处理线程里还引入过锁的顺序问题(线程锁死锁),两个锁互相等,现象和阻塞一样难查。

**修复**：改造为真正的异步调用(async 化的 LLM 客户端),重任务丢进 2-Worker 线程池跑,并加 BoundedSemaphore 信号量(processing_slot)限制同时进行的 LLM 高开销请求数——排队而不是无限堆。锁的顺序统一,避免互相等待。修复后多 POST 并发不再卡死。

**可讲价值**：说明你不只调通 API,还理解"异步框架里不能有阻塞调用"这条铁律,以及并发要靠限流而非无限扩展。

### D2 线程级用户身份泄漏：匿名请求继承了上一个用户的身份（越权隐患）

**现象**：匿名用户发出的请求,偶尔会表现出"已登录"的状态——能查到本不该查到的持仓类数据。时灵时不灵,极难复现。

**根因**：用户身份存在线程本地变量(thread-local)里,供工具随时取"当前是谁"。但请求处理完,线程回到线程池复用,线程本地变量**没被清理**——下一个匿名请求复用了这条线程,就继承了上一个用户残留的身份,造成越权误判。

**修复**：每次请求统一设置身份(set_current_user(user_id or None))——有身份就设、没身份就置空,从请求生命周期入口就把 thread-local 管死;LangGraph 图里的节点也显式绑定当前用户。修完用"匿名→带身份→再匿名"三轮 HTTP 场景回归,全链路都对。

**可讲价值**：这是并发安全 + 身份隔离的经典坑——凡是用"当前用户"的地方,必须随请求生命周期创建和清理,否则线程池复用就把 A 的身份带给 B。金融场景这等于潜在越权事故。

## 二、开发期：Agent 可靠性与反幻觉

### D3 让模型"自觉"处理资金操作 → 偶发放行错误（申购适当性）

**现象**：最初申购"能不能放行"这类判断曾依赖大模型"自觉"——模型偶尔不守纪律,把低风险测评的客户答成"可以买高 R 产品",或该走门控的不走,这正是金融场景最危险的偶发。

**根因**：能不能买是**确定性合规规则**(客户测评等级 ≥ 产品风险等级才行),但若交给大模型在函数调用里"自觉"判断、自觉调动账工具,LLM 是概率系统,再好的模型也有偶发失误,一次放错就是适当性违规。教训本质是:**能写死判断的规则(尤其监管红线),不该交给推理链赌概率**。

**修复**：把资金动账改成**确定性门控节点**(subscribe_node)——代码写死五步:归属 → 产品存在 → 适当性(测评等级不足→拦截转人工双录)→ 起购金额 → 验证码二次确认,全过才写持仓并留痕。更进一步、也更结构性:**申购/赎回/撤单根本不注册成 Agent 可调用的工具**,模型手里只有 4 个只读工具,放行在结构上不可能发生(见 F4-F6)。效果:适当性不足 → 拦截转人工、金额不足/验证码错误/重复持有 → 各自明确提示,离线门控场景测试全过。

**可讲价值**：这是"多 Agent 编排能加确定性护栏"的核心例证——把高风险动作从"模型自由决策"里摘出来,是 Agent 工程化 vs demo 的分水岭。

### D4 语义缓存串答：高相似问题命中到不该复用的旧答案

**现象**：两个问题字面/语义高度相似(余弦相似度高达 0.99),却命中了不该复用的旧缓存答错;更糟的形态是——换一个用户问同构问题,可能命中别人用户私有数据的答案。

**根因**：语义缓存只看"问题像不像",相似度高就返回缓存答案。但相似 ≠ 可复用——关键要素不同(年份/风险档位)、**用户不同**,答案都可能不该复用。相似度 0.99 的两句话可能是两个完全不同的东西,放在共享缓存里就会串答、甚至串用户。

**修复**：两层。一是**签名守卫**:对问题做关键要素签名,两句话签名不一致就拒绝命中,向量再像也不复用,守卫在 L1/L2 两个层级都生效(最初 L1 高阈值路径漏了守卫,补上)。二是理财域加**缓存隐私守卫**(cache/privacy.py):"我的持仓/验证码/动账金额"这类用户私有与动账问答,读写两侧都不进共享缓存——结构性不让私有答案进缓存,从根上消除串用户(见 F8)。

**可讲价值**：缓存领域"误命中比漏命中危害大一个量级"——漏命中顶多多花一次 LLM,误命中是反复给错误/别人的答案;金融场景的误命中可能等于把 A 的持仓答案返回给 B。你懂"什么该缓存、什么绝不缓存",而不只是会调相似度阈值。

### D5 实体替换：问 A 产品答成 B 产品（答非所问）

**现象**：用户问"稳盈添利30天保本吗",检索返回了别的产品片段,LLM 照单全收,答成别的产品。

**根因**：检索工具把召回内容无条件喂给 LLM,即使内容和查询点名的产品完全无关。RAG 的通病:检索到"别家的文档"+ LLM 顺从 = 答非所问。而且一旦模型看到了错误内容,事后纠正很难救回。

**修复**：加**实体对齐检查**——工具先解析查询里点名的产品(含目录别名),若该产品不出现在任何检索片段内容里,就**抑制**：不把其他产品内容喂给模型,明确提示"知识库暂无该产品资料,不要用无关内容冒充,可转人工"。问 A 不再答成 B。

**可讲价值**：RAG 必须做"查询实体 ↔ 检索内容"的对齐。**抑制(不给错内容)比事后纠正(验收拦截)更可靠**,因为模型一旦被错误内容污染就很难拉回来——这是反幻觉的前置防线。

### D6 反幻觉只靠 LLM 审查 → 又贵又不稳,改为双层（正则预检 + LLM 审查）

**现象**：最初所有答案都过 LLM 二次审查反幻觉,延迟高、成本高,而且偶尔漏判。

**根因**：反幻觉全押在"再调一次 LLM 判断"上。其实很多幻觉是**模式化的**,根本不用 LLM:数字断言(金额/期限/风险等级)有没有出现在检索上下文里、引用的来源是不是检索来源的子集、检索到很多却答"未找到"、长回答没带任何来源——这些用正则就能查。

**修复**：ReviewerAgent 分两层。第一层 QuickCheck 用正则做廉价预检,约六成请求直接通过、跳过 LLM 审查;剩下的才交给 Reviewer LLM(来源有效性/是否引用未提供来源/检索有货却答未找到)。reject 最多回环重写 2 次并注入上次反馈。确定性转人工/门控节点直接跳过 LLM 审核(静态话术无需反幻觉)。效果:幻觉在输出前被拦,审查成本压到低位。

**可讲价值**：反幻觉要"先廉价规则、再昂贵模型"分层,才能落地——全 LLM 审查贵且不稳,全正则又拦不住语义级幻觉。你理解成本与覆盖的取舍。

## 三、测试/上线期：检索与图谱的真实故障

### D7 检索"静默失效":能出结果但召回质量差(通道静默退化)

**现象**：检索系统部署后"看起来正常"——能出结果、不报错,但用户反馈答非所问。查了很久才发现是召回坏了。

**根因**：多个索引之间存在不一致,造成**静默退化**:向量索引重建时 metadata 没存 content 字段,而检索代码里有硬过滤依赖 content,导致向量通道永远返回空、系统悄悄退化成只剩关键词检索——因为还能出结果,所以一直没人发现。另有 BM25 字段名与 chunk 不一致导致跨文档去重与溯源错乱。

**修复**：统一所有数据源为同一份 chunks 处理产物、字段对齐;向量索引 metadata 补上 content;嵌入模型改为复用单例加载。修完逐个通道验证"各自都能独立出结果"。

**可讲价值**：检索系统里"静默退化"比"报错"可怕得多——报错你能看见,静默退化是系统不崩但质量差,很难察觉。排查不能只测"能不能出结果",要逐个通道验证,并检查索引字段是否对齐。

### D8 MMR 重排取索引吞掉 0：早期 FAISS 兜底路径必崩的隐藏 bug

**现象**：某种情况下早期 FAISS 兜底路径的检索结果第一条永远丢/报错，看起来像偶发。

**根因**：代码里取索引时用了 `r.get('faiss_idx') or default` 这类写法。Python 里 0 是假值——当合法下标就是 0(第一条向量)时,`or` 把它吞掉换成了默认值,第一条结果被错误处理。

**修复**：改成显式判空(`is not None`),不把 0 当假值。后来 FAISS 兜底路径已删除,Milvus 改为唯一后端,这个 bug 不再存在,但作为历史踩坑保留——它暴露的是对"0 是合法值、不能当假值"的边界意识。

**可讲价值**：看似一行的小 bug,暴露的是对"0 是合法值、不能当假值"的边界意识。你讲得出这个就证明代码不是照着抄的。

### D9 图谱只跑内存后端,Neo4j 上线后才发现查询语法炸

**现象**：Neo4j 容器拉起、灌库成功后,一问多跳问题报 Cypher 语法错误,链路中断;而之前一直用内存图谱降级,完全没暴露。

**根因**：Neo4jGraph 的路径查询写成 `shortestPath(...-[*1..$max_hops]->...)`——**Neo4j 的 shortestPath 变量长度范围不支持用参数**,必须内联字面量。内存图实现没有这个限制,所以测试一直用内存后端、单测全绿,真上 Neo4j 就炸。

**修复**：把变量长度范围改成内联整数(先 int() 强转再格式化进 Cypher)。修完用真实 Neo4j 库验证多跳查询(理财产品→存款保险、两跳路径、无实体返回 None)全通过,图谱证据正常注入。

**可讲价值**：这个故事最能说明"**后端真实环境和降级路径要分开测**"——内存降级掩盖了真实后端的 bug。凡是写了"自动降级",就一定要对真实主后端做一次端到端,而不是只测降级那条路。

### D10 Docker 镜像源不可达 → 配 registry 镜像源（部署）

**现象**：`docker compose up -d neo4j` 时镜像拉不下来,报网络/超时/403。

**根因**：所在网络直连 Docker Hub 及多个常见镜像源不通(阿里云 403、部分源 DNS 不通);镜像源配置曾放错层级(放 builder.gc 下不生效),且不同源稳定性差异大。

**修复**：先把 registry-mirrors 放到 daemon.json 顶层;再逐个实测候选镜像源(对目标镜像真实拉 manifest + blob 验证,而非只看能连通),选定一个匿名免 token、全链路 200 的源(proxy.vvvv.ee)配置,重启 Docker Desktop 后拉取成功。容器按 restart policy 自动拉起无损。

**可讲价值**：部署问题也讲判断——"源能连上"≠"能拉到这个镜像",要拿真实镜像做 manifest/blob 级验证;Docker Desktop 改 daemon.json 必须重启引擎才生效。
